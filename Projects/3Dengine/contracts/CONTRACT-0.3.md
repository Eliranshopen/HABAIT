# Contract for milestone 0.3 — a job on the disk
<!-- last-updated: 2026-11-17 · plan: development/plans/2026-11-16-pdf-to-360-engine-mcp.md §7.1 row 0.3, §4.3 item 1 · board: development/tasks/3dengine (card 03) -->

**What 0.3 is:** the job layer the real engine will run on. After it, a job is a folder that tells the whole truth about itself (`job.json`, `manifest.json`, `ledger.json`), one detached runner walks it stage by stage, and a runner that dies can be started again and continues from the same point: no finished stage is repeated and no paid call is billed twice. The stages themselves are still stubs; milestones 1.x–7.x replace them one by one WITHOUT changing this layer.

**What does not change:** the eight MCP tools, their inputs and results, the states and their percents, `job.json` as 0.2 defines it (fields are only added), the bridge and the app. Every test of milestones 0.1 and 0.2 keeps passing, the end-to-end test included.

**The closing test (plan §7.1):** kill the runner in the middle of a stage, start it again, and the job continues from the same point with no double billing.

**Reading order:** sections 10 to 16 were added after the first seven QA rounds of this milestone; section 17 is the eighth round, which passed. Each of them wins over everything before it. The lines of sections 1 to 9 that they changed carry a pointer in brackets.

## 1. One runner, a list of stages
- `engine/runner.mjs`, started DETACHED as `node engine/runner.mjs <job_id>`. It replaces `mcp/stub-runner.mjs` (delete that file; nothing else may start it).
- The stages, in order, are the working states of the job: `tracing`, `building`, `rendering`, then the wait `awaiting_approval` (a wait, not a stage), then `skinning`, `gating`, `finishing`, `packaging`, `qa`; after the last one the job is `done`.
- A stage is a module in `engine/stages/<stage>.mjs` that exports implementations by mode: today only `stub`. The runner picks `job.mode`. An implementation is `async run(ctx)` → `{ outputs: [{ path, sha256, bytes }], detail }`, where `ctx` gives `job`, `config`, `jobDir`, `stageDir` (`jobs/<id>/stages/<stage>/`), `paidCall(spec, fn)` (§3), `checkCancelled()` and `log(line)`.
- The stub implementation of every stage: waits `stub.stepSeconds` (or `ENGINE_STUB_STEP_MS`) in small slices while calling `checkCancelled()`, then writes `stages/<stage>/stub.json` (the stage, the job id, the attempt) as its one output. [§11.3: the output is byte-stable; it holds the stage, the job id, the inputs hash and the mode, not the attempt.] The three stages that cost money in the real engine (`skinning`, `gating`, `finishing`) also make ONE paid call each through `paidCall`, with the amount `stub.callUsd` (0 in the real settings; a test may set it).
- `awaiting_approval`: the runner writes the quote (as in 0.2) and polls for `approval`; everything 0.2 says about it holds (24 hours, then the runner exits; an approval or a new start brings a runner back).
- When the last stage is done the runner starts the local link (as in 0.2) and writes `result`.

## 2. `manifest.json` — what was really done
`jobs/<job_id>/manifest.json`, schema `habait/manifest.v1`, written atomically:
```json
{ "schema": "habait/manifest.v1", "job_id": "…", "rows": [
  { "stage": "tracing", "attempt": 1, "status": "done", "started_at": "…", "finished_at": "…", "seconds": 0.4,
    "inputs_sha256": "…", "outputs": [{ "path": "stages/tracing/stub.json", "sha256": "…", "bytes": 61 }],
    "cost_usd": 0, "runner_pid": 1234 } ] }
```
- A row is appended ONLY after the stage's outputs are on the disk. A stage that was interrupted leaves no row.
- `inputs_sha256` = sha256 of: the PDF's sha256, the apartment, the mode, the engine version, the stage name, and the `outputs` hashes of the previous stage's row (empty for the first).
- `attempt` counts how many times the runner STARTED this stage for this job (kept in `job.json` → `attempts: { "<stage>": n }`, raised before the stage starts).
- `cost_usd` = the sum of what this stage settled in the ledger during this row's attempt.
- **Resume rule:** before a stage, the runner looks for a `done` row of that stage whose `inputs_sha256` equals the current one and whose output files still exist with the same hashes. If found, the stage is SKIPPED: not run, not billed, its row untouched. Otherwise it runs, and a row whose inputs no longer match is kept and marked `"superseded": true`.

## 3. `ledger.json` — every paid call, reserved before it is sent
`jobs/<job_id>/ledger.json`, schema `habait/ledger.v1`, the same manners as the pipeline's own ledger (`pipeline/Habait/tour360/tools/file-ledger.mjs`: reserve before send, settle after), written atomically:
```json
{ "schema": "habait/ledger.v1", "job_id": "…", "cap_usd": 60, "rows": [
  { "seq": 1, "call_key": "…", "stage": "skinning", "provider": "stub", "what": "one stub call",
    "reserved_usd": 0.6, "reserved_at": "…", "status": "settled", "settled_usd": 0.6, "settled_at": "…",
    "answer_sha256": "…", "attempt": 1 } ] }
```
- `cap_usd` = `job.cost.cap_usd` (null before the approval).
- `paidCall({ key, provider, what, estimate_usd }, fn)`:
  1. `call_key` = sha256 of the stage name + `key` (the caller's stable description of the input).
  2. A `settled` row with this `call_key` exists and its answer is in `cache/<call_key>.json` → return the cached answer. No new row, nothing sent. **This is "no double billing".**
  3. A `reserved` row with this `call_key` exists (a runner died between reserve and settle): its outcome is unknown, so mark it `orphaned` and keep it. Then go on to 4. [§10.1 and §12.1: a row whose answer is in the cache is settled from it. §12.2: a reserved row that was never marked as sending is closed as never sent, not orphaned.]
  4. The cap: when `cap_usd` is a number and the ledger total (settled amounts, plus the reserved amount of every `reserved` or `orphaned` row) plus `estimate_usd` is above it → throw `BUDGET_CAP`. Nothing is reserved.
  5. Append a `reserved` row, write the file, THEN call `fn()`. [§10 rule 9 and §12.2: just before `fn()` the runner checks that it still owns the job and marks the row `sending_at`.]
  6. On success: write the answer to `cache/<call_key>.json`, then set the row `settled` with `settled_usd`. On failure: set the row `failed` with `settled_usd: 0` and rethrow. [§10.1, §12.1: the cache file holds the answer, what it cost and the `seq` of its row. §13.3: both writes are tried again when the job lock is busy.]
- A paid call can happen only after `approval` exists: `paidCall` in a job with no approval throws an `EngineError` with the code `BUDGET_CAP` and the message "no approved cap". No new reason code is added for this.
- `job.cost.spent_usd` = the ledger total of settled amounts, updated after every settle. [§10 rule 2 and §14.1: it is a COPY of the ledger's total; what the engine reports is always the ledger's total.]
- An `orphaned` row is never hidden: `engine ledger <job_id>` and the `job` CLI command print it, and it counts toward the cap.

## 4. Alive or not
- While a stage runs the runner writes `heartbeat_at` every `runner.heartbeatSeconds` (default 2), not only at a change of state. `runner.pid` is written beside `job.json` as in 0.2.
- `get_job`, `list_jobs` and the CLI add a computed field (never written to the file): `"runner": { "alive": true, "pid": 1234, "heartbeat_age_s": 1.2 }`. `alive` = the pid in `runner.pid` is a live process. [§10 rule 5: AND it gave a fresh sign of life.] For a terminal job or a job waiting for approval with no runner: `alive: false` is normal.
- A job whose state is a working state and whose runner is not alive is STALLED. It is not a new state: `get_job` says so through `runner.alive: false`, and the CLI prints the word. Nothing restarts a stalled job by itself.

## 5. One heavy stage at a time (root §12)
- `rendering` is a heavy stage (in the real engine it is Blender). The settings name them: `"runner": { "heartbeatSeconds": 2, "heavyStages": ["rendering"], "heavyLock": ".runtime/heavy.lock" }`.
- Before a heavy stage the runner takes the lock file (it holds the pid and the job id; a lock whose pid is dead is stale and is taken over). [§10 rule 5: also a lock that was not refreshed for `runner.staleMs`. §10 rule 13: a holder that lost it stops its heavy stage.] While another job holds it, the runner stays in the state BEFORE the heavy stage, keeps its heartbeat, and writes `"waiting_for": "heavy-lock"` into `job.json`; the field is removed when the stage starts. The lock is released when the stage ends, fails or the runner is cancelled.

## 6. Start, resume, cancel
- `start_simulation` with a PDF whose job exists:
  - the job is `done` → `created: false`, nothing starts;
  - the job is in a working state or `awaiting_approval` and its runner is alive → `created: false`, nothing starts;
  - the same but the runner is NOT alive → a runner is started; the result carries `resumed: true`;
  - the job is `cancelled`, `failed` or `review` → it is RESTARTED: `reason` cleared, the state set back to the state of the first stage with no valid manifest row (or `awaiting_approval` when the first three are done and there is no approval), a runner started, `resumed: true`. This replaces the 0.2 rule that a cancelled job stays cancelled.
- `approve_paid_stage` starts a runner when none is alive (as in 0.2).
- `cancel_job`: as in 0.2; the runner sees it within one heartbeat, releases the heavy lock, leaves no manifest row for the interrupted stage, and exits. [§10 rule 6: a stage whose paid call was already made writes its outputs and its row.]
- CLI additions: `resume <job_id>` (the same as the restart above), `ledger <job_id> [--json]`, and `job <job_id>` prints the stages with their manifest rows, the ledger total, the orphaned rows and STALLED when it applies.
- **A stage that throws:** the job becomes `failed` with `reason: { code, message }`. An `EngineError` keeps its own reason code (`BUDGET_CAP` for the cap). [§10 rule 3: reaching the cap does not fail the job, it goes back to `awaiting_approval`.] Any other error gives the new, generic code `STAGE_FAILED`, which is added to the reason-code list in `job.schema.json` as the fourteenth code (contract 0.2 §2 listed thirteen). The interrupted stage leaves no manifest row, and the heavy lock is released.

## 9. Decisions taken during the build (2026-11-16)
They complete the sections above; where a line here and a line above disagree, this one holds.
- **`queued` counts as a working state** for §4 and §6: a job whose runner died before the first stage is stalled and can be resumed.
- **A changed output sends the runner back.** If an earlier stage's output files changed while the job is in a later state, the runner returns to that stage: no later stage is ever skipped on a stale row.
- **A runner resumed inside `rendering` waits there** for the heavy lock, not in the state before it.
- **A paid call is keyed on the stage's inputs hash**, so the key is the same across attempts of the stage.
- **Money is summed in micro-dollars**, so three calls of $0.6 are exactly $1.8.
- **`start_simulation`'s result gained `resumed`** (its output schema too).
- **Three defects the kill tests found, fixed in the engine:** a runner killed while it held `job.lock` blocked every resume for 10 seconds (a lock whose pid is dead is now taken over at once); on Windows a reader holding `job.json` open made the atomic rename fail and the runner crash (a write now retries for about 3 seconds, and the runner waits out a short file error); the heavy lock was released before `job.json` left `rendering`, so two jobs could both show `rendering` for a moment (the lock is now kept until the state has changed).

## 10. After the first QA round (2026-11-16) — the fresh reviewer's verdict was FAIL
Report: `development/tasks/3dengine/logs/0.3/qa-live.md` (about 85 real kills). Each line below is binding and wins over anything above.
1. **A call whose answer is already cached is never sent again.** The cache file `cache/<call_key>.json` holds the answer AND its `settled_usd`, and is written before the row is settled. On resume, a `reserved` row whose cache file exists is SETTLED from it (`"recovered": true`), the cached answer is returned, nothing is sent. Only a `reserved` row with NO cache file becomes `orphaned`. (Found: a kill after the cache write and before the settle billed the call twice.)
2. **`cost.spent_usd` is derived, never accumulated.** It is recomputed from the ledger (the sum of settled amounts) when a runner starts, after every `paidCall` (a cache hit included) and before the job is set `done`. (Found: a kill between the settle and the update left it too low for good.)
3. **Reaching the cap is not a dead end.** When a reserve would cross the cap, the runner does not fail the job: it puts it back to `awaiting_approval` with `reason: { code: "BUDGET_CAP", message }`, a new quote (`estimate_usd` = everything the ledger counts toward the cap plus the estimate that did not fit; `range_usd` = that amount up to the larger of that amount and the previous upper bound; `"cap_reached": true`), appends the old approval to `approvals` (a history list) and sets `approval` to null. A new `approve_paid_stage` whose cap is at least the new estimate clears `reason` and continues the job from the same stage. Section 3 item 4 and section 6's line about a throwing stage do not apply to `BUDGET_CAP` any more. (Found: a job that hit the cap after an orphaned reservation could never get a larger cap.)
4. **A lock file is never empty.** *(Replaced by contract 1.4 §11: since milestone 1.4 the lock is a folder with one entry named after its holder; every hold begins with one exclusive step (a prepared folder renamed onto the path), and a stale hold is broken, never handed over. The rule below is how a lock FILE of the older engine is still read.)* `job.lock` and the heavy lock are created atomically together with their content (write a temp file, then link or rename it into place so that creation fails if the lock exists). A lock file that is empty or unreadable is stale after 1 second. (Found: 1 hard kill in 60 left an empty `job.lock` that blocked a resume for 10 seconds.)
5. **Alive means a live pid AND a fresh heartbeat.** A runner whose `heartbeat_at` is older than the larger of 10 seconds and 5 × `runner.heartbeatSeconds` is not alive, whatever its pid says (a recycled pid must not make a dead runner look alive). The runner keeps the heartbeat while it waits for an approval and while it waits for the heavy lock. The holder of the heavy lock refreshes it at every heartbeat; a heavy lock not refreshed for that long is stale.
6. **A cancel during a paid call.** The call cannot be recalled, so the stage writes its outputs and its manifest row IS written: it is what was really done and paid. The runner then stops before the next stage. "No row for the interrupted stage" holds for a stage whose outputs were not written.
7. **The closing test gains five parts**, with real kills and the same discipline: (8) a kill after the cache write and before the settle (hook `ENGINE_TEST_PAUSE_AFTER_CACHE_MS`): after the resume the call has ONE row, `settled`, `recovered: true`, and the stub's call counter shows the call ran once; (9) a `spent_usd` on the disk that disagrees with the ledger is corrected on resume and at `done`; (10) the cap is reached (a temp setting makes the calls cost more than the approved cap allows): the job returns to `awaiting_approval` with the new quote and the reason, a larger approval continues it to `done`, and the total never crosses a cap that was in force; (11) an empty `job.lock` on the disk does not block a resume for more than about 1 second; (12) a `runner.pid` that names a live foreign process (the test's own pid) with a stale heartbeat is not alive, and a resume starts a runner.
8. **A kill soak** (`tests/soak/kill-soak.mjs`, `npm run test:soak -- --kills N`; not part of `npm test`) kills runners at random moments, some of them inside the three pauses of a paid call, and checks after every kill: the three files parse, no `call_key` settled twice, no stage with two valid rows, a call sent again only where a reservation's outcome was unknown, `spent_usd` equal to the settled sum, a resume never blocked by a lock, and every job reaching `done`. Round 2 ran 156 kills and then 67 more with no violation.
9. **One runner owns a job, and checks it before every write.** Rule 5 makes a runner that is alive but silent (a blocked thread, a suspended machine) look dead, so a second runner can be started for its job. `runner.pid` is the ownership record. A runner claims it under the job lock; under that same lock it checks that the file still names it before it changes `job.json`, before it reserves a paid call, AGAIN just before it sends that call, and before it appends a manifest row. `checkCancelled()` and the wait for the heavy lock check it too, and a stage calls `checkOwner()` before it writes an output after a paid call (rule 6 forbids `checkCancelled()` there). A runner that finds another pid there stops (`stopped: superseded` in `runner.log`) and writes nothing more; it gives `runner.pid` back only when the file still names it.
10. **Paid calls of a replaced runner.** A call it had reserved and not sent is NOT sent: its row is closed as `failed` with `"not_sent": true` and nothing billed, also when the second runner had already marked it `orphaned` (the outcome is known now, the hold is freed). A call that was already on the wire cannot be recalled: when its answer comes back the row is settled with `"late": true`, because it is what was billed; the second runner may have sent the same call meanwhile. A late answer never replaces the answer the second runner has already cached for that call (the cache is written under the job lock): a stage that runs again must find that answer, or the call would be sent a third time. That is the one case left in which a call can be billed twice, and both rows show it. (Rules 9 and 10 were found by the main session before the second QA round: rule 5 alone let two runners work on one job.)
11. **Known limit.** The ownership check and the write that follows are two steps inside a lock that is itself taken over after 10 seconds. A process suspended INSIDE a locked section (a few milliseconds long) for longer than that can still write once after it wakes. The same holds for a stage's own output files, which are written outside the lock: a replaced runner already past its last check can finish one write, the row of the runner that owns the job then no longer matches the bytes, and the resume rule runs that stage again (its paid calls come from the cache); a real stage avoids it by writing each attempt into a folder of its own. A plain file system cannot close this; a paid call that must never be doubled needs the provider's own idempotency key where the provider has one, to be settled with the first real paid stage.
12. **The closing test gains part 13, the soak a second phase.** The test hook `ENGINE_TEST_FREEZE_MS` with `ENGINE_TEST_FREEZE_AT` BLOCKS the runner's thread (no heartbeat), once in the life of a runner, at `<stage>` (the start of that stage) or at `<paid stage>:reserved` (after the reserve, before the send); nothing happens unless both are set. (13) on a temp home with `runner.staleSeconds` 1: (a) a runner blocked at the start of `building` is replaced; it wakes while the second runner owns the job, writes no row, leaves the second runner's `runner.pid` alone and stops as superseded; (b) a runner blocked between the reserve and the send of the `skinning` call is replaced; the call is sent ONCE, by the second runner, the first row ends `failed` + `not_sent`, and no reservation is left open. `npm run test:soak -- --freezes N` repeats the takeover at random points and checks after each: one valid row per stage; rows by the replaced runner only for the stages before the one it was blocked in; every paid call sent exactly once; no `orphaned` or `reserved` row left; `spent_usd` equal to the settled sum; the replaced runner gone by itself.
13. **A runner that was silent can lose the heavy lock, and then it stops its heavy stage.** Rule 5 lets another job take the heavy lock from a holder that did not refresh it for `runner.staleMs`, also when that holder is alive. The holder finds out at its next heartbeat or at its next check (`checkCancelled()`, and once more before the manifest row): it stops the heavy stage, writes NO row for that attempt, leaves the other job's lock alone, waits for the lock in the heavy state and runs the stage again. So two jobs never have overlapping rows of a heavy stage. What this cannot undo: a tool that a real heavy stage started keeps running until the stage stops it, so a real heavy stage must stop its child processes when the check throws; the pipeline's own machine-wide Blender lock stays the second line. Part 14 of the closing test: job A's runner is blocked at the start of `rendering` with the lock in its hand; job B takes the lock over and renders; A wakes, gives up attempt 1 with no row, and renders again as attempt 2 after B has finished.

## 11. After the second QA round (2026-11-16) — the verdict was FAIL on the stability of the gate itself
Report: `development/tasks/3dengine/logs/0.3/qa-live-r2.md` (164 real kills, about 104 real takeovers and lock losses, real suspension of processes; the kill-and-takeover claim itself was not refuted). Each line below is binding; where it disagrees with section 10, this one holds.
1. **The gate passes every time (defect G1).** A test never decides on ONE look at something a live runner changes by itself: `job.lock` (taken for a few milliseconds at every heartbeat) and `runner.alive` with a small `runner.staleSeconds` (a late heartbeat on a loaded machine). It waits, within a bound, for the look that shows the expected state; a thing that is really wrong never shows it. The freeze tests do not depend on the clock: `ENGINE_TEST_FREEZE_WAKE` names a file, the block ends when the test creates it, and `ENGINE_TEST_FREEZE_MS` is only the upper bound.
2. **`cost.spent_usd` is computed inside the job lock (observation O3).** `syncSpent` reads the ledger while it holds the job lock, the lock every ledger write happens under, so two runners that sync at the same moment cannot leave a stale total behind. It stays outside the ownership check on purpose: it writes a value derived from the ledger, and a replaced runner that has just settled a late answer must be able to make the total true.
3. **A stage's output is byte-stable (observation O7).** The same inputs give the same bytes at every attempt: no attempt number, no time, no random value in an output. Then a stage that runs again, because its output was damaged or deleted, reproduces its output; the rows of the stages after it stay valid, none of them runs again, and no paid call is made a second time. The stub writes `{ stage, job_id, inputs_sha256, mode }`. A stage that cannot be byte-stable changes the inputs of every stage after it, and by section 9 their paid calls are then made again: for a real stage that is a cost decision, taken with its milestone (the render, the AI look).
4. **The late answer is testable (observation O1).** A third freeze point, `<paid stage>:sent`: the call was sent and its answer is in hand, nothing is recorded yet.
5. **Known limit: a lock held by a LIVE process (observations O2, O4).** `job.lock` and the heavy lock's guard are taken over at once from a dead holder, after 1 second when empty, and after 10 seconds from a live one. So a runner suspended inside a locked section, or a dead holder whose pid was reused by another live process, blocks other writers for up to 10 seconds; a tool call that needs the lock in that time fails with `lock busy` (a JSON-RPC internal error) and succeeds when it is repeated. Not changed here: a shorter time would make it easier to take a lock from a holder that is only slow.
6. **The closing test: part 13 gains case (c), part 15 is new.** (13c) a runner blocked at `skinning:sent` is replaced and the second runner makes the same call; when the first wakes, its row is settled `late`: the call has two settled rows and two sends, `spent_usd` counts both, and the answer the second runner cached is kept. (15) while the runner is dead, the output of `tracing` is damaged and the output of `building` is deleted: both stages run again and reproduce their bytes, no later stage runs again, the ledger does not grow. The soak's takeover phase wakes the blocked runner at a random moment (at once, a little later, after `done`) and knows the `:sent` point: a call has a second settled row only when that row is `late`, and is sent a second time only then.

## 12. After the third QA round (2026-11-16) — the verdict was FAIL on one defect of the ledger
Report: `development/tasks/3dengine/logs/0.3/qa-live-r3.md` (about 87 real kills and 83 real takeovers and lock losses; the gate itself was stable, 18 runs of 18). Each line below is binding; where it disagrees with an earlier section, this one holds.
1. **No reservation is ever left open (defect D1).** When a runner asks for a paid call, every OTHER `reserved` row of that call is closed in the same locked step, whether or not the answer is found in the cache. (The defect: with the answer found, a row left by a killed runner stayed `reserved` for good and kept counting toward the cap.) The cache file names the row its answer belongs to (`seq`): that row is the one settled from it (`recovered`, and `late` too when it had been presumed lost), wherever it stands among the rows. A cache that names a failed row, a row that does not exist, or a settled row that recorded another hash is not an answer.
2. **A reservation says whether its send had started.** Just before the send, under the job lock and after the ownership check, the row gets `sending_at`. A `reserved` row of another runner WITHOUT that mark was never sent: it is closed as `failed` + `not_sent` and nothing is held for it. One WITH it has an unknown outcome: `orphaned`, kept, counted toward the cap (section 3). So a runner that dies between its reserve and its send leaves no hold. The hook `ENGINE_TEST_PAUSE_AFTER_RESERVE_MS` pauses after the mark; the freeze point `<stage>:reserved` is before it.
3. **How often a call can be sent.** A call is sent again only when the outcome of every earlier send of it is unknown at that moment (an `orphaned` row), or when its cached answer is gone. Every send has its own row, marked before the send. A second SETTLED row of one call exists only as a `late` row (section 10 rule 10) or as a row with `resend_of` (item 4).
4. **The cache is the only copy of a paid answer (observation O-A).** When the cache file of a settled call is deleted or changed and a stage needs that answer again, the call is made again and billed again; the new row names the row it repeats (`"resend_of": <seq>`). Nothing in the engine deletes or rewrites a cache file of a settled call.
5. **One call per key at a time.** A stage does not make two calls with the same key at the same moment. If it does, the second closes the first one's reservation and the first stops before its send (`STAGE_FAILED`): never two sends. [Replaced by §13.1: this could not happen with real timing, and both calls were sent. Two such calls are now one call.]
6. **A runner started for a job that has ended leaves at once** and does not take `runner.pid`. (Started while another runner was finishing the job, it used to hold the pid file of a `done` job for a moment.) [§16.1 completes this: the state is looked at again inside the locked claim.]
7. **Known limit, added (observation O5 of round 2).** With a small `runner.staleSeconds` a healthy runner on a loaded machine can look dead for a moment. A runner started in that moment takes the job and the first one stops (section 10 rule 9): safe, and the default stays 10 seconds.
8. **Tests (observations O-C, O-D).** No part of the closing test has to catch a short window any more: parts 6, 9 and 15 block the runner with the freeze hook at the point they need and wake it themselves, and part 11's bounds are 5 seconds (the defect was 10). Part 16 is new: (a) defect D1 with three real runners; (b) a runner killed while it is blocked before its send: the next runner drops the reservation, sends the call once, and nothing is held. The soak's takeover phase kills the SECOND runner in one takeover of three (half of those kills aimed inside one of its pauses) and lets a third runner finish; it fails on a `reserved` row at `done`, on an `orphaned` row that was never marked as sending, and on more sends than marked rows. A test run that is killed from outside leaves the detached runners and static servers of its temp homes behind, because its `after` hooks do not run: `tests/CLAUDE.md` gives the command that lists them.

## 14. After the fifth QA round (2026-11-17) — the verdict was FAIL on the copy of the spent total
Report: `development/tasks/3dengine/logs/0.3/qa-live-r5.md` (about 95 real kills and 88 real takeovers; the gate was stable, 13 runs of 13 and 2 more under CPU load; round 4's defect D2 answered with 2, 3 and 10 calls). Each line below is binding; where it disagrees with an earlier section, this one holds.
1. **What was spent is what the ledger says (defect D3).** The ledger's settled total is the truth; `cost.spent_usd` in `job.json` is a COPY of it. The copy is written (a) in the same locked step as every ledger change that moves the settled total, (b) when a runner starts work on a job and before it sets the job `done`, and (c) by every read of an existing job through the engine: `get_job`, `list_jobs`, `get_result`, the job in the answers of `start_simulation`, `approve_paid_stage` and `cancel_job`, and the CLI's `job` and `jobs`. Each of those reports the ledger's total and puts the copy right when it differs; when the copy cannot be written at that moment (the job lock is busy) the answer is the ledger's total all the same. So what the engine REPORTS is the ledger's settled total at that moment (only when the ledger file itself cannot be read at that moment does it report the copy). The copy in the file can be behind only when a process died between the ledger write and the copy, two writes a few milliseconds apart inside one locked step, and only until the next such read. A program that reads `job.json` by itself, as the agent's bridge does, can see the copy behind for that time. (The defect: the copy was made at the end of the paid call. A replaced runner that settled a late answer on a job already `done` and was killed before that end left the total too low for good, because a job that has ended gets no runner.)
2. **A cache carries an amount (observation O-J; this narrows section 13 item 2).** For a row whose send had started, the cache file the engine wrote is the record of the answer AND of what it cost: a row recovered from it is settled with the file's amount. A file whose amount is not a number of zero or more is not an answer. [§15.1 replaces this rule: an amount is a number from 0 to 1,000,000, and a missing one is not an amount.] Beyond its shape, and its hash for a settled row, the engine does not defend against a cache file that was edited by hand.
3. **The close of a failed send (observation O-L).** It is tried again like the settle when the job lock is busy, and the caller always gets the send's own error. A row that cannot be closed within 30 seconds stays reserved with its mark, and the next attempt marks it orphaned.
4. **Known limits, added.** (a) **Billed above the estimate (observation O-I).** The cap is checked against estimates, before a call. A provider that bills more than the estimate takes the counted total above the cap by the difference; the next call is then refused. The stub bills exactly its estimate, so "the total never crosses the cap" holds in 0.3. A real paid stage reserves its maximum; the rule is set with the caps milestone. (b) **A quote written at a cap stop (observation O-K)** is what was needed at that moment. Rows that are resolved later (a late answer, a reservation closed as never sent) can make the real need lower; the quote is not rewritten, and an approval of the quoted amount continues the job. (c) **A runner that waits for a busy job lock** cannot write its heartbeat either, so after `runner.staleMs` it looks dead and another runner can take the job. That is safe by section 10 rule 9.
5. **Tests.** Part 17 of the closing test: runner 1 is blocked at `skinning:sent`, runner 2 finishes the job, runner 1 is woken with a pause after its settle and is killed inside that pause; `job.json` says 2.4 before the kill and after it, and `get_result` says 2.4. Then the copy is set back by hand, as a kill between the two writes would leave it: `start_simulation` (which starts nothing for a done job), `get_job`, `list_jobs` and `get_result` each report 2.4 and put the copy right.
6. **A file that another process holds for a moment.** Windows answers an open or a rename of such a file with `EBUSY`, `EPERM`, `EACCES`, or with an error Node has no name for (`UNKNOWN`; seen on 2026-11-17 when another process had the file mapped). All four are passing errors: the atomic writes, the locks and the runner's loop wait them out. `runner.pid` is written atomically (temp file, then rename), so it is never seen half-written. The closing test of milestone 0.1 puts its tracked report file back with the same patience; one run in three of the gate failed in the live home on exactly that, and left the tracked file modified.
