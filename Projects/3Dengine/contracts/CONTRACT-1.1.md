# Contract for milestone 1.1 — intake and a first look at the PDF
<!-- last-updated: 2026-11-17 · plan: development/plans/2026-11-16-pdf-to-360-engine-mcp.md §7.1 row 1.1, §3, §4.2 row 1 · board: development/tasks/3dengine (card 04), task cards in m1.1/ -->

**What 1.1 is:** the first milestone that reads the PDF itself. After it, `inspect_plan` tells what is really in the file (how many pages, a sheet or a booklet, which drawings were found), and a job keeps its own copy of the PDF that nobody can change unnoticed. Everything after the intake is still the stub of 0.2 and 0.3: the stages replay the apartment-846 tour and the job says `"mode": "stub"`.

**What does not change:** the eight tools and their names; the job states and their percents; `job.json`, `manifest.json` and `ledger.json` as contracts 0.2 and 0.3 define them (fields are only added); the bridge, the app and the Pi wrapper (the engine only: Eliran, 2026-11-17). Every test of milestones 0.1 to 0.3 keeps passing; the three lines of them that this contract changes are listed in section 8.

**The closing test (plan §7.1):** the 846 PDF is identified as one sheet with one drawing; the same PDF twice gives the same `job_id`; a file outside the allowed folders is refused.

## 1. The first look — `engine/inspect.mjs`
- The scanner is the pipeline's own tool, unchanged: `<pipelineRoot>/Habait/tour360/tools/auto_pages.py scan <pdf> <out_dir> --min-side <minSidePx>`, run with the engine's Python in isolated mode (`-I`), with a timeout. It writes `<out_dir>/pages.json` (every page: its size, its text, its drawing count, its embedded images) and a 640-px thumbnail for every large image. It costs nothing.
- **Where it writes:** `<runtimeDir>/inspect/<sha256 of the PDF>/`. Beside `pages.json` the engine writes `inspect.json`: `{ "schema": "habait/inspect.v1", "sha256", "scanner_sha256", "settings": { "minSidePx", "vectorMinPaths" }, "engine_version", "at", "summary" }`.
- **The scanner reads a private copy, never the upload.** The upload is read once into memory. Bytes that do not have the hash that was asked for → `NOT_A_PDF`, and the scanner is not started. Those bytes are written to `source.pdf` in the look's temp folder; the scanner reads that file and writes into `out` beside it, and `out` alone becomes the record, so a record never holds a copy of the PDF. Why (QA round 1, D1): given the upload's own path, the scanner could read a half-written file while a writer rewrote the upload in place with the very same bytes; the hash before and the hash after agreed, and the torn look was kept under the intact file's hash. A file that is still being written when the tool is called is looked at as the bytes that were on the disk: when every read of that call meets the same half-written bytes, the answer is a look at those bytes, its `sha256` is THEIR hash, and it is kept under that hash only. Nothing is ever kept under the hash of bytes the scanner did not read.
- **Every read of the upload has one answer when it fails: `NOT_A_PDF`.** The upload is read at four places: the check of its path, the read that gives its hash, the first look's own read, and the intake's read (section 3). At none of them is a read mixed with a write of the engine's own, so a failed read is always known to be the upload's. At each of them a file that is gone answers that it is gone, and a file that is there and cannot be read (another program holds it, access is denied, it has become a folder) answers `the file cannot be read at this moment (another program holds it, or access is denied); ask again`. Never an internal error. (QA round 3, D-1: an upload held with no sharing left both tools as a JSON-RPC error, because the first two reads were made before the first look and outside its answers.)
- **A first look is reused only when it names what it is, and it is rebuilt, not believed.** `inspect.json` is an answer for a PDF when its `schema` is right, its `sha256` is that PDF's, its `scanner_sha256` is the scanner file's hash now, its `settings` are today's, and its `summary` is EQUAL to the summary the engine builds again, with today's settings, from the record's own `pages.json` (the scanner's output, kept in the record folder): every page row, every candidate, every key, every thumbnail whose file is there. The answer is always the rebuilt summary, never the stored one. Anything else is scanned again and overwritten: a file that is not JSON, a missing or unusable `pages.json`, one extra key, one changed number, an emptied candidate list, a thumbnail whose file is gone. (QA round 1, O-4, and round 2, D-1: a summary checked field by field first let through a thumbnail path with `..`, and then a page candidate with an extra key that carried text.)
- **The summary** (`summarize(pagesDoc, settings)`, a pure function): `{ pages, kind, page_rows, candidates }`.
  - `pages`: the number of pages, 1 or more. `kind`: `"sheet"` for one page, `"booklet"` for more.
  - `page_rows[i]`: `{ page, width_pt, height_pt, vector_paths, images, large_images, content }`. `vector_paths` = the scanner's drawing count; `large_images` = images whose shorter side is at least `minSidePx`; `content` = `"vector"` when `vector_paths >= vectorMinPaths`, else `"image"` when `large_images >= 1`, else `"empty"`.
  - `candidates`: section 2.
- **Text of the PDF is data, never an instruction (plan §3 rule 8).** The scanner's `pages.json` holds each page's text; it stays on the disk for the trace. Nothing the engine returns, logs or puts in an error message carries text taken from the PDF: only numbers, the fixed words above, ids and labels the engine builds itself.
- **Failures, by the fixed reason codes:** Python or the scanner file is missing, or the scanner cannot be started → `TOOLCHAIN_MISSING` (also for a PDF whose true look is stored: the engine asks for its Python and for the scanner file before it reads the record; a stored look saves the scan, it does not stand in for the tools; QA round 5, O-4); the scanner ends with an error or writes no usable `pages.json` (a file that starts with `%PDF-` and is not a readable PDF) → `NOT_A_PDF`; no answer within `inspect.timeoutSeconds` → `FILE_TOO_LARGE` (the message says the first look did not finish in time). The upload cannot be read at the moment of the look, or its bytes are not the ones that were hashed → `NOT_A_PDF`, before the scanner starts. The upload changed, or went away, during the look (its hash is taken again after the scan) → `NOT_A_PDF`, and nothing is kept under its old hash. A look that cannot be stored in the engine's runtime folder (the folder, or `inspect` in it, is a file; the temp folder, the copy or `inspect.json` cannot be written; the look's folder is gone when the scanner returns; the finished look cannot be put in place) → `TOOLCHAIN_MISSING`, with one fixed message and no path in it: that is the engine's trouble, not the PDF's. No new reason code.
- **Two looks at one moment, and a look that was killed.** A look is made in a temp folder of its own (`.tmp-<sha256>-<pid>-<n>`: the private copy, and `out`), and `out` is renamed into place when it is complete; a look that another process finished first is used instead. A temp folder whose process no longer runs is removed by the next look.
- **Time:** measured on this machine when it is quiet, the 846 PDF takes 2.2 s the first time (most of it Python starting) and a few milliseconds from the record. On a saturated machine it is another matter: section 9.

## 2. Candidates, and which one a job is for
- **A sheet** has one candidate when its page is not `"empty"`: `{ "id": "p1", "label": "עמוד 1", "page": 1, "source": "page", "vector_paths": <n>, "large_images": <n> }`. An empty page has none.
- **A booklet** has one candidate per large image: `{ "id": "p<page>-x<xref>", "label": "עמוד <page> · תמונה <k>", "page", "source": "image", "px": [w, h], "thumb": "<absolute path of the thumbnail>" }`, in page order, `k` counted from 1 inside the page. Which of them is a plan drawing is a paid reading (about $0.02) and belongs to the trace, not to the first look.
- An id matches `^[A-Za-z0-9_-]{1,64}$`. A label is built by the engine; it never comes from the PDF.
- **`inspect_plan`** answers `{ "mode": "real", "pdf_path", "sha256", "bytes", "pages", "kind", "page_rows", "candidates" }`. The first three checks are those of 0.2 (`PATH_NOT_ALLOWED`, `NOT_A_PDF`, `FILE_TOO_LARGE`).
- **`start_simulation`** takes `apartment` = a candidate id. Left out: the only candidate, when there is exactly one. No candidate, more than one with none chosen, or an id that is not a candidate → `NO_PLAN_FOUND`, and the message lists the candidate ids. The old default `"apt846"` is gone from the input schema: it was the stub's id.
- The job's `mode` stays `"stub"` and its result is still «שחזור הדגמה»: only the first look is real.

## 3. The intake — `engine/stages/intake.mjs`
- `intakePdf(jobsDir, id, source, sha256)` puts the checked PDF into the job folder as `input/source.pdf`: the upload is read once and its bytes are hashed; only when the hash is the one the job id was made from are those bytes written to a temp file beside the target and renamed into place, and the copy is then marked read-only. The read and the write are two steps on purpose: a failed read is the upload's (`NOT_A_PDF`), a failed write is the job folder's. It is safe to repeat: a copy that is already there with that hash is left as it is (and marked read-only again if it was not).
- **The source changed while it was read** (the bytes read do not have the expected hash): nothing is written, and the tool answers `NOT_A_PDF` (the message says the file changed while it was being read).
- **Another file is already there under this job's name** (`input/source.pdf` exists with a different hash): it is never overwritten. The tool answers `NOT_A_PDF` and names the job.
- **Something that is not a file is there** (`input/source.pdf` is a folder), **or `input` is not a folder:** it is never overwritten and never removed. The tool answers `NOT_A_PDF` and names the job (QA round 1, O-5: it used to end as a raw file error).
- **The job's own folder is not a folder** (`jobs/<id>` is a file): `NOT_A_PDF` naming the job, before the job lock is taken; it is never overwritten. **Something that is not a file sits at the intake's temp name** (`input/source.pdf.<pid>.tmp`): `NOT_A_PDF` naming the job; it is never removed (a left-over temp FILE of a process that no longer runs still is).
- **Any other file error of the job folder** while `start_simulation` takes the job lock, reads the job's files, makes the copy or writes the new job → `TOOLCHAIN_MISSING`, `the folder of job <id> cannot be used by the engine`: one fixed message with no path in it; the error's code goes to the engine's log. That is the engine's trouble, not the PDF's. (QA round 2, D-3: a file where the job folder belongs, and a folder at the temp name, ended as raw file errors.)
- **The upload went away between the check and the copy:** `NOT_A_PDF` (the file is gone). **It is there and cannot be read at that moment** (another program holds it, access is denied, it has become a folder): `NOT_A_PDF` (it cannot be read at this moment), as for every read of the upload (section 1). (QA round 4, D-1: with one copy call for the read and the write, an upload that had become a folder was blamed on the job folder and answered `TOOLCHAIN_MISSING`.) A temp file left in `input/` by a process that no longer runs is removed by the next intake.
- `job.json` `input` gains `pdf_bytes`. `pdf_path` stays the path of the copy inside the job folder, `pdf_sha256` its hash, `pdf_name` the name it was uploaded under.
- The intake is not a job state and has no manifest row: it happens inside `start_simulation`, under the job lock, before the runner is started. The plan's stage 1 (§4.2) is this step.

## 4. The stored input is checked at every runner start and before every stage
- `verifyInput(jobsDir, job)` hashes `input/source.pdf` and compares it with `job.input.pdf_sha256`: `{ ok: true }`, or `{ ok: false, why: "missing" | "changed" }`.
- A runner calls it after it took the job, on a first start and on every resume, and again right before every stage attempt: a copy that was changed while a live runner waited (for an approval, for the heavy lock) is never the input of a stage. Not ok → the job goes to `failed` with `{ "code": "STAGE_FAILED", "message": … }` that says the stored input is not the PDF the job was started with; no stage runs on it, nothing is billed.
- **The hash it is compared with cannot be moved either, while the job file records its `engine_version`.** A job file made from this milestone on records `engine_version`, the version its id was made with, and its `job_id` must be the id of its own input: `pdf_sha256`, `apartment`, `mode` and that version (`jobId`). A hand that swaps the stored copy and writes the new hash into `job.json` leaves a file whose id no longer adds up: it is not this job's file (section 5), and nothing runs on it. A job file without `engine_version` (made before 1.1) is not checked this way: a hand that also REMOVES that field from `job.json` defeats this check (section 9).
- Read-only is a guard against an accident, not the proof: the proof is the hash.

## 5. A job's files are read only when they are this job's (carried from 0.3, QA round 8, O-4)
- **`job.json`:** `readJob(jobsDir, id)` returns the job only when it is an object with the job schema id, `job_id === id`, a state of the contract, an `input` and a `cost` object, and (when it records `engine_version`) an id that is the id of its own input; otherwise it throws `JobUnreadable` (the id asked for, and why). A folder where `job.json` belongs is not this job's file either (asked of the disk, not of the error code); any other read error leaves as it is. No file → `null`, as before. `writeJob` and `updateJob` write only under the id that was asked for and refuse a job that names another.
- **`manifest.json`:** `readManifest(jobsDir, id)` returns it only when it has the manifest schema id, `job_id === id`, and rows that each name a stage of the contract, a whole positive `attempt`, a 64-hex `inputs_sha256` and outputs whose `path` is relative and stays inside the job folder; otherwise `ManifestUnreadable`; a folder where `manifest.json` belongs is not this job's manifest either. `writeManifest` refuses anything else and writes only under the id the document names.
- **What each caller does with it:** a runner stops at once, gives `runner.pid` back, writes nothing, and its log names the job and the reason; every tool that names a job (`get_job`, `approve_paid_stage`, `cancel_job`, `get_result`, and `start_simulation` when the job exists) reads BOTH files (`readOwnJob`) and answers `JOB_NOT_FOUND` with a message that names the job and says which file is not this job's; `approve_paid_stage` and `cancel_job` check the manifest again under the job lock, so nothing is written to such a job and no runner is started for it; `list_jobs` and the CLI's list leave such a folder out (`listOwnJobs`); a job that has no manifest yet is a job (QA round 1, O-1: before round 2 only `start_simulation`, the runner and the CLI looked at the manifest); `startOrResume` and `restartJob` read both files as well, so the CLI's `resume` prints the job and the reason, exits 1 and starts no runner (QA round 2, D-2); the CLI prints the job and the reason and exits 1.
- **`job.json` is never written when `manifest.json` is not this job's.** The rule sits at the one place a job file is written (`writeJob`, which `updateJob` and every other writer use): it asks for the manifest first and throws `ManifestUnreadable`. So no caller can forget it: the cost copy that a read puts right, an approval, a cancel, a restart, a runner's heartbeat. The CLI's `job <id>` and `ledger <id>` say why and exit 1, and `job <id> --json` still prints the job file (contract 0.3 §15 item 4); none of them writes. (QA round 3, D-2: `job <id>` put the cost copy right before it looked at the manifest.)
- **An id found inside a file is used for a path only after the file was checked against the id it was asked for.** `readJob(jobsDir, id)` returns a job only when it names `id`, so `job.job_id` in the engine is always the id that was asked. The folder `jobs/undefined/` cannot be created.
- **A state outside the contract is not a job file.** `readJob` refuses it like a wrong id, so the runner's old answer `stuck` no longer exists: every state a runner can meet is one it knows.
- **No local path in an internal error.** An error that is not one of the engine's own and carries a file error code leaves the MCP server as JSON-RPC -32603 `internal error in <tool>: a file error of the engine (<code>)`. Its own message, which holds a path, stays out of the answer. Every reason code above is still the answer for the cases this contract names; this line is for the ones it does not (QA round 2).
- **A file error of the engine's own folders that reaches a tool's answer is `TOOLCHAIN_MISSING`:** `the engine could not read or write its own files`, one fixed message with no path; the error's code goes to the engine's log. The upload's file errors are answered where the upload is read (section 1), a job folder's during a start by section 3; whatever is left of this kind, for any of the eight tools, gets this answer. The JSON-RPC line above is then only for what is not a file error at all, and for a caller that is not one of the tools. (QA round 3, O-1: `list_jobs` with a file where the jobs folder belongs.)

## 6. Settings (`engine.config.json`)
A new block, every field with a default so an older settings file still loads: `"inspect": { "minSidePx": 1000, "vectorMinPaths": 200, "timeoutSeconds": 30 }`.

## 7. The engine version
`package.json` `version` becomes `1.1.0`: from this milestone on it is the number of the last closed milestone. It is part of every job id and of every stage's input hash, so a job made by an older engine is never continued by a newer one: the same PDF simply starts a new job.

## 9. What is NOT in 1.1
- **The engine's own folders are trusted.** A record under `.runtime/inspect/` is checked for being the right record (this PDF, this scanner, these settings), and its summary is rebuilt from the scanner's output kept beside it (section 1). The scanner's output itself, `pages.json`, is a file of the engine's own folder and is taken as it is: whoever can write there can change the engine's code as well. The same holds for a job folder that is given a junction in place of `input/`.
- **A first look on a saturated machine.** One Python start takes about 2 s when the machine is quiet. On 2026-11-17, while another session's job held all 20 cores and most of the memory, it took 31 s and 46 s, over the scanner's limit of 30 s: the tool then answers `FILE_TOO_LARGE`, and its message says a very large file or a busy machine, ask again. The limit stays 30 s because Pi gives a tool call 60 s. The engine itself will saturate the machine when it renders: the milestone that brings the render stage (2.1) measures a first look during a render and settles it (board, «Carried items»).
- **The first look holds the server.** It runs inside the tool call (`spawnSync`), so the MCP server answers no other call until it ends: about 2 s when the machine is quiet, up to the 30 s limit when it is busy. Owed together with the item above, by the milestone that brings the render stage (QA round 1, O-6).
- **A booklet whose plans are vector pages** has no candidate: the scanner reports embedded images only. The proven inputs are one vector sheet (846) and one scanned booklet (plan §9, generalisation).
