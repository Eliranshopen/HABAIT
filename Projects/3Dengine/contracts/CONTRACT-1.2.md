What this milestone writes is the engine's one way to start it (`engine/trace.mjs`, the command `node engine/cli.mjs trace`) and the proof.

**What does not change:** everything under `pipeline/` but that one line; the eight MCP tools, the job states, `job.json`, `manifest.json`, `ledger.json`; the runner and its stages (the stage `tracing` is still the stub: making it real is milestone 1.3); the bridge, the app and the Pi wrapper (the engine only: Eliran, 2026-11-17). Every test of milestones 0.1 to 1.1 keeps passing.

**The closing test (plan §7.1):** exit 0; 10 of 10 rooms, every printed dimension within 1 % (the measured number: 0.83 % at most): first from a saved reading, at $0, then from one fresh reading (about $0.09, inside a cap Eliran gives).

## 1. How the engine starts the reading tool — `engine/trace.mjs`
- **One function starts it: `runTrace(config, options, deps)`.** Nothing else in the engine starts `auto-trace.mjs`. The command is `node <pipelineRoot>/Habait/tour360/tools/auto-trace.mjs <pdf> --out <outDir> --id <id>` and then, by the options: `--vlm-file <file>` (a saved reading), `--no-judge` (the vision judge is off), `--budget <usd>`, `--env-root <dir>`, `--ledger <file>`. The working folder is the pipeline root. The environment is the caller's, with the engine's pointers on top (`pipelineEnv(config)`: Python, the Node libraries, the legal folder and the rest) and `PYTHONIOENCODING=utf-8`.
- **Every value handed to the tool is an absolute path, a checked id or a number.** `pdf`, `outDir` and the saved reading are resolved to absolute paths; `id` matches `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` (default `apt-new`, the tool's own; never a leading hyphen: the tool finds its flags by their text anywhere in the command, so an id `--no-judge` would switch the judge off and an id `--budget` would take the cap away); the cap is a finite number. So no value can be read by the tool as one of its flags.
- **What is checked before anything starts** (a `TraceUsageError`, nothing is created): the PDF is a file; a saved reading, when given, is a file that holds one JSON object; the id has the shape above; the output folder does not exist, or is an empty folder.
- **The differences from the pipeline's own runner** (`stepTrace` in `run-project.mjs`), on purpose: no `--review-queue` (the portal's queue; in the engine a failed reading becomes the job's own state, milestone 1.3); no `--spec` and no `--type` (a booklet with several apartments is a later milestone); the cap is never defaulted to the tool's $1 (section 2).

## 2. A run costs nothing unless it was told to pay
- **Two kinds of run, decided at this one place.** A run is PAID only when the caller passes `go: true` AND a cap `budgetUsd` that is a finite number above 0 and not above `trace.maxBudgetUsd` (section 5). Every other run is FREE.
- **A free run cannot pay, by construction.** The tool is given `--budget 0`, its own check then refuses every vision call before it is made (a call is estimated at $0.02 or more); `--env-root` points at the run's own empty output folder, so no keys file is found; and the names in the settings' `keys` list are taken out of the tool's environment. The tool's ledger file is never created.
- **A paid run** is given `--budget <cap>`, `--env-root <envRoot of the settings>` and `--ledger <outDir>/ledger.json`. The tool reads the keys by name itself, books every vision call in that ledger BEFORE the call (a row `reserved`), settles it after, and stops with exit 4 before a call that would pass the cap. The engine never reads a key.
- **A run that would need to pay and was not told to does not start.** When there is no saved reading, or the judge is on, a free run is known to need a vision call: `runTrace` starts nothing and answers the outcome `DRY` with what would be called (one reading when there is no saved one, up to `judgeRuns` runs of the judge, each estimated at $0.02) and the cap rule. `go` without a cap, a cap that is not a number above 0, or a cap above `trace.maxBudgetUsd` is a `TraceUsageError`: nothing starts.
- **The case that cannot be known before the run** (a booklet, whose pages the tool sorts with one vision call even when a saved reading is given): on a free run the tool is stopped by its own budget check or by the missing key, and the outcome is `NEEDS_PAID_RUN`.

## 3. What is read back, and what is returned
- **The tool's own output goes to a file, never to the caller:** `<outDir>/auto-trace.log` (its stdout and stderr, in order of arrival). It holds room names and other text read from the PDF, which is data (plan §3 rule 8) and stays on the disk beside the tool's other files.
- **A result is read only from the folder this run created, and only when it names this run.** After the tool ends, `<outDir>/index.json` is read: it must be an object whose `input` is this run's PDF path and whose `id` is this run's id, with a `status` of `PASS` or `FAIL` and a list `plans`; each plan's folder must be inside `outDir`, and its `trace-check.json` and `report.json` are read from there. Anything else (no file, not JSON, another input or id, a folder outside) is the outcome `RESULT_UNREADABLE`: never a PASS, never a crash.
- **What `runTrace` returns:** `{ outcome, exit, seconds, paid, outDir, logFile, result }`. `exit` is whatever exit code the tool's process reported, or `null` when it reported none; after a stop it is the code the operating system gave the killed process (1 on Windows), not a code of the tool's own. A caller decides by `outcome`, never by `exit`. `result` is `null` unless the outcome is `PASS` or `FAIL`, and then: `{ status, spentUsd, plans }`, each plan `{ k, page, status, rounds, rooms, fixtures, scalePxPerCm, checks: { total, failed }, roomCount: { expected, got }, dims: { count, failed, maxPct }, couldNotRead, judge: { state, runs, mismatches }, files: { dir, plan, overlay, report, traceCheck } }`. `k` is the plan's number; `couldNotRead` and `mismatches` are COUNTS; `judge.state` is `skipped`, `unavailable` or `report`.
- **No field can carry text taken from the PDF.** The result is built field by field from numbers, the fixed words above, and paths the engine put together itself. The tool's labels (`floor_label`, `dwelling_label`), its room names, its failure lines and its `could_not_read` lines are never copied. The same holds for every error the module throws and every line it prints or logs.

## 4. Outcomes, exit codes, and a run that is stopped
- **The tool's exit code is passed through and named:** 0 → `PASS`; 5 → `FAIL` (its own check found failures); 3 → `NO_PLAN_FOUND`; 4 → `BUDGET_REACHED` (on a free run: `NEEDS_PAID_RUN`); 2 → `USAGE`; 1, or any other code → `STEP_FAILED` (on a free run whose log holds the tool's fixed sentence about a missing key: `NEEDS_PAID_RUN`). Exit 0 or 5 with a result that cannot be read is `RESULT_UNREADABLE`; exit 0 with a result that says `FAIL`, or 5 with one that says `PASS`, is `RESULT_UNREADABLE` too.
- **Changed by milestone 1.3 (contract 1.3 §2):** a free run now gives the tool a fixed word under the fal key's name (not a key), so the tool refuses a vision call by its budget check, exit 4. `NEEDS_PAID_RUN` is exit 4 on a free run and nothing else; exit 1 is `STEP_FAILED` whatever the log holds, and the module no longer reads the log. The command also carries `--rounds` (the setting `trace.rounds`), and an output folder whose path has a character outside ASCII is refused before anything starts.
- **Outcomes of the engine's own:** `DRY` (section 2: nothing started); `NOT_STARTED` (the tool's process could not be started); `TIMEOUT` (no end within `trace.timeoutSeconds`); `CANCELLED` (the caller's signal).
- **A run that is stopped leaves no process behind.** On a time-out or a cancel the tool's whole process tree is stopped (on Windows `taskkill /PID <pid> /T /F`; elsewhere the process group), the function waits for the tool's process to end (up to 15 s), and then returns. The folder of a stopped run is not read.
- **The run does not block the caller's event loop:** the tool is started with an asynchronous spawn and awaited (a runner that starts it in milestone 1.3 keeps its heartbeat).
- **What these outcomes become for a job** (states and reason codes) is milestone 1.3. In 1.2 they are reported as they are.

## 5. Settings (`engine.config.json`)
A new block, every field with a default so an older settings file still loads: `"trace": { "timeoutSeconds": 1500, "maxBudgetUsd": 1, "judgeRuns": 3 }`. `timeoutSeconds` is the pipeline runner's own limit for this step; `maxBudgetUsd` is the tool's own default budget, kept as the most a single reading may be allowed; `judgeRuns` is the tool's default and is only used to say what a paid run would call.

## 6. The command — `node engine/cli.mjs trace`
- `trace <pdf> --out <dir> [--id <id>] [--vlm-file <file>] [--no-judge] [--budget <usd>] [--go] [--json]`. Without `--go` it is a free run, or a `DRY` answer when the configuration needs a vision call (root §5: dry-run by default, the paid path only behind an explicit `--go`). With `--go` it needs `--budget`.
- **It prints** one line per fact: the outcome, the seconds, and for a result the rooms, the checks, the room count, the printed dimensions and the largest percent, what was spent, the output folder and the log file. `--json` prints the object of section 3. A `DRY` answer prints what would be called, the cap rule, and for each key name of the settings `present` or `missing` (names only, the way the readiness command does).
- **Exit code:** 0 for `PASS` and `DRY`; 5 for `FAIL`; 3 for `NO_PLAN_FOUND`; 4 for `BUDGET_REACHED` and `NEEDS_PAID_RUN`; 2 for a `TraceUsageError`; 1 for everything else. An option typed with no value after it (`--out` at the end) is the command line's own error, as for every command of the engine since 0.1: exit 1, not 2.
- It is an operator's command: the PDF is whatever path the operator names. The agent's door is still the MCP tools, where a PDF passes the inbox check and the intake (contract 1.1).

## 9. What is NOT in 1.2
- **The reading as a job stage.** The runner's `tracing` stage is still the stub. Making it start `runTrace` on the job's own copy of the PDF, and turning the outcomes into job states and reason codes (`NO_PLAN_FOUND`, `TRACE_GATE_FAIL`, `review`), is milestone 1.3.
- **The cache of a reading** (a second run of the same PDF pays nothing) is milestone 1.4. In 1.2 a saved reading is a file the caller names.
- **The job's own ledger.** A paid reading is booked in the tool's ledger file in the run's folder. Booking it in a job's `ledger.json`, under the job's cap and approval, comes with the stage (1.3) and the money milestones (4.x).
- **A booklet.** The proven input is the 846 sheet. A booklet needs one more vision call to sort its pages; the wrapper answers `NEEDS_PAID_RUN` for it on a free run and it is not proven here.
- **The judge as a gate.** The tool reports the judge beside its mechanical check and does not fail on it (its own rule, «a report until stable»). 1.2 changes nothing in that.
- **A reading through fal's router with real money.** The fal route is proven by the measured runs of 2026-11-06 to 08 and, for its header, by part 3; the paid reading of this milestone went the direct way.
- **An output folder whose path holds letters outside ASCII.** The tool's raster step cannot open its own image under such a path (OpenCV), and a good PDF answers `STEP_FAILED`. A folder with Hebrew letters and spaces for the PDF and the saved reading works. A job's folder is named by the engine in ASCII; the path of the engine home itself is not checked (QA, O-1; owed by milestone 1.3, whose stage is the first to give the tool a job's folder).
- **`NEEDS_PAID_RUN` after exit 1 is read from the tool's log** (its fixed sentence about a missing key). In the review nothing of a PDF or of a reading reached that log, in seven tries of five kinds. The log is still the tool's free text, so milestone 1.3, which turns outcomes into job states, decides this one without it or shows why it cannot be forged (QA, O-6). Done in 1.3: decided by the exit code alone (contract 1.3 §2).
- **`readTraceResult` reads what the real tool writes; it is not a guard against another writer of the folder.** It takes the same PDF spelled another way (letter case, slashes, a relative path), a `FAIL` result with no plan at all, and a plan folder that is a junction to somewhere else. The real tool writes none of these (QA, O-5; for milestone 1.3 to weigh when a stage trusts a result).
- **The settings' three numbers** may be written as numeric strings or one-element lists (`"30"`, `[5]`): the loader's own reading of a number since 0.2; the bounds hold (QA, O-7).
- **A saturated machine.** The time limit is 1,500 s; a reading took 492 s while other sessions rendered. What a job does when the machine is that busy belongs to the render milestone (2.1) with the other saturated-machine items (board, «Carried items»).
