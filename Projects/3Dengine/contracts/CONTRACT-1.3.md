# Contract for milestone 1.3 — the trace gate
<!-- last-updated: 2026-11-18 · plan: development/plans/2026-11-16-pdf-to-360-engine-mcp.md §7.1 row 1.3, §3, §4.2 row 2 · board: development/tasks/3dengine (card 06), task cards in m1.3/ -->

**What 1.3 is:** the reading of the drawing becomes the first REAL stage of a job. A job of mode `real` reads its own copy of the PDF with the reading tool, and what the reading gives decides what the job does next: a reading that passes its own check goes on; a reading that fails it hands the job to a person (`review`) and never reaches the build; a PDF with no plan drawing ends the job with `NO_PLAN_FOUND`.

**What does not change:** the eight MCP tools, their names and their inputs; the job states and the fourteen reason codes; `manifest.json` and `ledger.json`; the reading tool and everything under `pipeline/`; the bridge, the app and the Pi wrapper (the engine only: Eliran, 2026-11-17). A job of mode `stub` behaves exactly as before, and `stub` stays the mode of a new job unless the settings say otherwise, so the agent still gets the replay of 846 and every test of milestones 0.1 to 1.2 keeps passing with no assertion changed (the two lines of 1.2's unit tests that this contract changes are listed in section 7).

**The closing test (plan §7.1):** a PDF with no drawing answers `NO_PLAN_FOUND`; a saved reading with a dimension changed by hand ends the job with `TRACE_GATE_FAIL`; in both cases Blender is not started.

## 1. Which jobs read for real: the mode of a job
- **The settings say which mode a NEW job gets:** `"mode": "stub"` or `"real"` in `engine.config.json`; `stub` when the field is absent, so an older settings file still loads. `start_simulation` makes the job with that mode, and `engine_status` reports it. The mode is part of the job id (contract 0.2), so the same PDF is one job as `stub` and another as `real`.
- **In mode `real` every stage must be real.** The runner asks the stage's module for its `real` implementation (`implFor`, unchanged); a stage that has none ends the job `failed` / `STAGE_FAILED`, as contract 0.3 says. There is no falling back to a stub: a real job never returns the replay of 846, and never shows a stub's quote. After this milestone a real job reads the drawing and, when the reading passes, stops at `building` that way. Each later milestone moves that line by one stage.
- **The real home stays `stub`** until the chain can show something (the preview, milestone 3.x). A real job exists today in a home whose settings ask for it: the closing test's, and an operator's.

## 2. The wrapper of the reading tool, tightened for a job — `engine/trace.mjs`
Three changes of the module milestone 1.2 wrote, each owed to that milestone's review.
- **`NEEDS_PAID_RUN` is decided by the tool's exit code, never by its log** (review of 1.2, O-6). A free run still gives the tool a budget of 0 and an env root with no keys file. In place of a key it now gives the tool a fixed word under the fal key's name (`free-run-no-key`; the OpenRouter name stays absent): the tool then passes its own «is there a key» question and reaches its budget check, which refuses every vision call with exit 4 before any request is made. So on a free run exit 4 is `NEEDS_PAID_RUN`, and exit 1 is `STEP_FAILED` whatever the tool's log holds. The module no longer reads the log. No real key is in a free run's environment, as before.
- **The self-correction rounds are a setting:** `trace.rounds` (section 5), given to the tool as `--rounds`.
- **An output folder whose path has a character outside printable ASCII is refused before anything starts** (review of 1.2, O-1): a `TraceUsageError` that says the reading tool cannot write its images there; nothing is created. The PDF and a saved reading may live in any folder.

## 3. The reading as a stage — `engine/stages/tracing.mjs` (`real`), `engine/readings.mjs`
- **What it reads:** the job's own copy of the PDF (`input/source.pdf`, contract 1.1), never the upload.
- **Where it writes:** a folder of this attempt, `stages/tracing/attempt-<n>/`, which only the stage and the tool write. `runTrace` refuses a folder that is not empty, so two attempts never share one, and a result is read only from the folder this attempt made.
- **Where the reading comes from:** the saved reading the engine holds for this PDF: `<readingsDir>/<sha256 of the PDF>.json`. `savedReadingFor(config, sha256)` answers `found` (with the file), `none`, or `bad` (something is there and it is not a reading: not a file, not JSON, not an object with a list of rooms). In this milestone a file gets there by a hand or a test; keeping the readings the engine paid for is milestone 1.4.
- **It never pays.** The run is free: the saved reading, the judge off, no go and no cap. With no saved reading the stage starts nothing and the job ends `failed` / `BUDGET_CAP`, its message saying that a reading of this drawing has to be paid for and that the engine does not pay for one inside a job yet. Paying inside a job needs the job's approval and caps (milestones 4.2 and 4.3). Until then a reading is paid for by the operator's own command (`node engine/cli.mjs trace … --budget <usd> --go`, contract 1.2).
- **What it gives the tool:** `runTrace(config, { pdf, outDir, id, vlmFile, judge: false, signal })`, with `id` = the job id (sixteen hex characters, built by the engine).
- **ONE table turns the outcome into what the job does** (`OUTCOMES` in the module; the stage decides by `outcome`, never by `exit` or by anything the tool printed):

| Outcome of the reading | The job | Reason code | A later stage |
|---|---|---|---|
| `PASS` | goes on: the stage returns its outputs | — | may start |
| `FAIL` (the tool's own check found failures) | `review` | `TRACE_GATE_FAIL` | never |
| `NO_PLAN_FOUND` | `failed` | `NO_PLAN_FOUND` | never |
| no saved reading (nothing is started), `DRY`, `NEEDS_PAID_RUN`, `BUDGET_REACHED` | `failed` | `BUDGET_CAP` | never |
| `NOT_STARTED`; an output path the tool cannot write to | `failed` | `TOOLCHAIN_MISSING` | never |
| a saved reading that is not a reading; `TIMEOUT`; `STEP_FAILED`; `USAGE`; `RESULT_UNREADABLE`; a reading that traced more than one plan | `failed` | `STAGE_FAILED` | never |
| `CANCELLED` | whatever stopped it (next line) | — | — |

- **A reading that is stopped.** While the tool runs the stage asks the runner twice a second whether it must stop (`checkCancelled()`: the job was cancelled, another runner took it over, the heavy lock was lost). When it must, the stage stops the tool and everything the tool started, waits for it, writes nothing, and passes on exactly what the runner threw. A passing file error of that question (the job file held for a moment by another process) is not a stop.
- **On `PASS` the outputs are** the plan (`plan-1/plan.general.json`), the overlay (`plan-1/overlay.png`), the report (`plan-1/report.json`), the check file (`plan-1/trace-check.json`) and the reading the tool used (`plan-1/vlm.json`), each as a path relative to the job folder. The runner hashes them from the disk and writes the row (contract 0.3). A job reads ONE drawing: a result with no plan or with more than one is not a pass.
- **On `FAIL` the stage throws `ReviewNeeded`** (section 4) with `TRACE_GATE_FAIL`, a message made of numbers (how many checks failed of how many, how many of them printed dimensions), and the files a person needs, where they exist: the report and the overlay.
- **No text of the PDF leaves the stage.** A reason message is one of the fixed sentences of the module, with numbers; the `review` record holds paths the engine built; the runner's log gets the same. Room names, labels and the tool's own failure lines stay in the tool's files in the attempt folder (plan §3 rule 8).

## 4. `review`: a stage can hand a job to a person
- **`ReviewNeeded(code, message, files)`** (`engine/jobs.mjs`) is what a stage throws when its own gate refused and a person has to look. `code` is a reason code of the contract; `files` maps a name to a path relative to the job folder.
- **The runner ends the job in `review`** where it already turns a stage's error into a state: the state `review`, `reason: { code, message }`, and a record `review: { stage, attempt, files }`. No manifest row is written for that attempt, no later stage starts, nothing is billed, the heavy lock is given back. The runner's answer is `review`.
- **The `review` record is checked wherever a job file is read or written** (`checkJob`): it may be there only while the state is `review`; `stage` is a stage of the contract, `attempt` a whole positive number; `files` has only the names `report` and `overlay`, each a path of the form `stages/<stage>/attempt-<attempt>/…` with no `..` in it. A job file that breaks this is not this job's file (contract 1.1 §5).
- **Restarting it** is what contract 0.3 §6 says for `review` already: `start_simulation` with the PDF again, or `engine resume`, sets the job back to the first stage with no valid row; the reason and the `review` record are cleared. The same saved reading gives the same failure again: the reading has to be replaced first.
- `contracts/job.schema.json` gains the optional field `review`.

## 5. Settings (`engine.config.json`)
Every new field has a default, so an older settings file still loads: `"mode": "stub"` (section 1); `"readingsDir"` (a path, relative to the engine home unless absolute; when absent it is `readings` inside the runtime folder); and in the `trace` block `"rounds": 3` (a whole number from 1 to 9, the tool's own default).

## 6. The engine version
`package.json` `version` becomes `1.3.0` (contract 1.1 §7).

## 7. Tests
- **The closing test** `tests/stages/m1.3.test.mjs` and `tests/stages/m1.3-pass.test.mjs` (two files, so the two real readings run side by side): the real MCP server, a real runner, the real reading tool and Python, on a temp engine home whose settings say `mode: real` and `trace.rounds: 1`, with saved readings put in its readings folder. Both start their home with `tests/stages/real-home.mjs` (test only). One round bounds the time of a failing reading by a setting: every round is a whole trace again, about a minute on a quiet machine. For this changed reading the tool has no correction to try after its first round, so the result is the same at the default of three.
  1. The 846 PDF with `tests/fixtures/apt846/changed-dimension-reading.json` (the saved reading with ONE printed dimension changed by hand): the job ends `review` with `TRACE_GATE_FAIL`; the report and the overlay are in the job folder where the `review` record says; the manifest has no row; the job's file never showed `building` or `rendering` (Blender is not started); the ledger has no row.
  2. A PDF with no drawing: `start_simulation` answers `NO_PLAN_FOUND` and makes no job (contract 1.1), on the same home.
  3. A PDF that has a drawing and no saved reading: the job ends `failed` with `BUDGET_CAP`; no attempt folder was made (the tool never started); the ledger has no row.
  4. (the second file) The 846 PDF with the true saved reading: `tracing` ends with a manifest row whose five outputs are on the disk with their hashes and whose plan has 10 rooms; the job then stops at `building`, `failed` / `STAGE_FAILED` (no real build yet); the ledger has no row.
  5. In all of them: no answer of a tool, no job file and no line of the runner's log holds a room name of the reading.
- **Unit tests:** `tests/unit/tracing-stage.test.mjs` (every row of the table with a fake `runTrace`; the stop; a marker sentence in every text field of a fake result; `savedReadingFor`), `tests/unit/review.test.mjs` (the runner's path to `review` and the restart; the `review` record wherever a job file is read or written; the mode of a new job, through the tools), and new cases in `tests/unit/trace.test.mjs` (section 2 and the three settings of section 5). `tests/unit/intake-wiring.test.mjs` pins the changed reading: its hash, and that it differs from the saved reading in the two values only.

## 8. What is NOT in 1.3
- **Paying for a reading inside a job.** Section 3. The tool's exit 4 on a paid run (`BUDGET_REACHED`) has its row in the table and is proven with a fake tool; no job reaches it for real before milestones 4.2 and 4.3.
- **Keeping a reading** (the engine's own cache, keyed by the PDF and the engine version, and a second run that pays nothing) is milestone 1.4. So is the day's date that the tool writes into the plan it traces (`plan_meta.trace_date`): the same reading traced on another day gives other bytes of `plan.general.json`, which a stage's outputs should not do (contract 0.3 §11.3). It costs nothing while no paid stage follows the reading; 1.4's own line is «a second run returns the identical plan».
- **The stages after the reading.** A real job stops at `building` (section 1).
- **A booklet, and choosing among several drawings.** The stage reads one drawing; the tool's `NO_PLAN_FOUND` (its exit 3) is its answer for a booklet with no plan page, which needs a vision call and so cannot be reached free. The closing test's «no drawing» is the first look's answer (contract 1.1); the stage's row is proven with a fake tool.
- **`readTraceResult` as a guard against another writer** (review of 1.2, O-5). The attempt folder is made by the stage and written only by the tool; a job's folder is the engine's own and is trusted as contract 1.1 §9 says.
- **The agent's side.** The bridge and the app do not show a `review` record yet (the engine only). The field is in the job file for the milestone that returns to the agent side.
- **A reading on a saturated machine.** The time limit is the wrapper's 1,500 s (board, «Carried items», card 08).

## 9. Decisions taken during the build (2026-11-18)
- **A real job is a job of mode `real`; no mixing inside one job.** A job that ran some stages for real and showed the stub's replay for the rest would put real numbers beside a demonstration. The mode says which it is, for the whole job.
- **A job does not pay for a reading yet.** The board's card is of tier T0 (no money); the rules of money inside a job are milestones 4.2 and 4.3, reviewed at tier T2. The plan's contract of `start_simulation` («up to $1 for the reading») is theirs to build.
- **Each tier of tests runs once in a gate (Eliran, 2026-11-18).** During this milestone's gate he was shown what in the process costs time and is not critical, and chose one thing: `npm test` once and `npm run test:stages` once, a run repeated only when it failed or was cut, and the live home after a merge given the readiness command only. This gate had already run the fast suite five times; the rule holds from here on (the board's `run-tasks.md`, step 3).
- **QA (2026-11-18, on `ef2d2dc`): PASS, no defect, in one round.** A fresh reviewer ran the gate itself, each tier once, on a machine at 1 to 28 % load (the stage tests 10 of 10 in 131 s; `npm test` 410 of 410, line coverage 99.75 %, 100 s; the soak with 0 violations) and started the real tool ten times. Four failing readings went through one job (a marker in every text field with a changed dimension, the same after `start_simulation` and after `engine resume`, a reading with a room removed): each ended `review` / `TRACE_GATE_FAIL` in an attempt folder of its own, with no manifest row, no ledger row, no later stage, and the marker in no job file or tool answer. A cancel during a reading left no process and no row; a hard kill of the runner and a resume used a new attempt folder. 40 forged tool results and 88 expectations on hand-edited `review` records broke nothing; a free run's environment held only the fixed word. It read the soak's dump and the changed check and agrees: the mark was written before the send, and a send with no mark is still caught at the next check. Its six observations: O-1, a room with an unknown `type` passes the tool's own check, which sees geometry only (owed by the milestone that builds from the plan: card 08 of the board); O-3, `trace.rounds` takes `true`, `[4]` and `"0x3"` because the settings' numbers go through `Number`, and the tool still gets a whole number from 1 to 9 (owed by card 07, which adds settings); O-4, its kill of a runner left no orphan tool, so a tool of a dead runner that still writes was not seen live (a new attempt has a new folder); O-2, O-5 and O-6 need nothing (a `FAIL` with no plan gives `review` with no files, and the real tool cannot answer so; a saved reading is parsed twice; `review: null` is allowed in any state). Report: `development/tasks/3dengine/logs/1.3/qa-live.md`.
- **The reading tool's free refusal is its own budget check.** With a fixed word in place of a key the tool refuses by exit code, so the engine reads no free text of the tool to learn why a run stopped.
