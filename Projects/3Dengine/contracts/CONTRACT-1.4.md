# Contract for milestone 1.4 — a saved reading
<!-- last-updated: 2026-11-18 · plan: development/plans/2026-11-16-pdf-to-360-engine-mcp.md §7.1 row 1.4 · board: development/tasks/3dengine (card 07), task cards in m1.4/ -->

**What 1.4 is:** the engine keeps the reading it paid for. A reading is what the vision model read from the drawing of a PDF (room labels, fixed elements, printed dimensions); it is the one thing in the reading of a drawing that costs money and that the model does not give twice the same. With a kept reading the same PDF is read by the model once, and the same reading always gives the same plan, byte for byte.

**What does not change:** the eight MCP tools; the job states and the reason codes; `manifest.json` and `ledger.json`; the outcome table of the reading stage (contract 1.3 §3); the rule of the paid path (free unless a go AND a cap: contract 1.2 §2); the bridge, the app and the Pi wrapper (the engine only: Eliran, 2026-11-17). A job still never pays for a reading (contract 1.3 §3).

**The closing test (plan §7.1):** a second run on the same PDF books $0 and returns the identical `plan.general.json`.

## 1. The store — `engine/readings.mjs`
- **One kept reading per PDF**, in a folder named by the PDF: `<readingsDir>/<sha256 of the PDF>/`, with two files.
  - `reading.json`: the reading exactly as the reading tool wrote it (the `vlm.json` of the run that made it), byte for byte. It is what a later run hands the tool.
  - `record.json` (`habait/reading.v1`): `pdf_sha256`; `reading_sha256` and `reading_bytes` of the file beside it; `reader` (section 2); `read_at` (the instant the model answered: the reading's own `_meta.at`, or the moment of an import when the reading carries none); `plan_date` (the day written into the plan traced from this reading: section 3); `saved_at`; `source` (`paid` or `imported`); `cost_usd` (what the reading call cost; 0 for an import); `model` (the model id the reading names, when it is shaped like one; else null); `engine_version` (which engine kept it: a note, not part of the key).
- **`findReading(config, pdfSha256)` answers one of four things, and the record is checked, never believed:**

| Status | When | A job (section 5) | The command (section 4) |
|---|---|---|---|
| `found` (with the file and the record's date) | the record names this PDF, the reading file has the hash and the size the record states, it parses as a reading (an object with a list of rooms), and the reader is today's | reads from it, free | reads from it |
| `none` | there is no folder for this PDF, or it holds neither file | `failed` / `BUDGET_CAP` | as 1.2: a reading has to be paid for |
| `stale` | everything adds up, and the reader that made it is not today's | `failed` / `BUDGET_CAP`, its own sentence | says so; a reading has to be paid for |
| `bad` | anything else: a file where the folder belongs (the layout of 1.3), one file of the two, a record that is not JSON or names another PDF, a reading whose bytes are not the record's | `failed` / `STAGE_FAILED` | says so; not used |

- **Nothing of a reading's text is returned, thrown or logged** by the store: a status, numbers, dates, hashes and paths the engine built. `model` is copied only when it is shaped like a model id (letters, digits, `. _ / : -`, at most 80 characters).
- **`keepReading(config, { pdfSha256, readingFile, source, costUsd })`** copies the bytes of a reading into the store and writes the record. The reading first, the record last, a pair that was cut in the middle is `bad` or `none`, never `found`. The new pair is written whole, under temp names, before anything the folder held is touched, so a write that fails leaves the old pair standing. Under one lock per PDF (section 11).
- **A reading that was paid for is never destroyed.** When the folder already holds a pair and the new reading is other bytes, or was made by another reader, the old pair is moved into `superseded/<n>/` (n counts up) before the new one is written. The same bytes by the same reader again: nothing is written.
- **Where the store lives:** `readingsDir` of the settings (contract 1.3 §5), by default `readings` inside the engine home's runtime folder. It is not in git: a reading holds text of a PDF. Each engine home has its own.

## 2. The reader, and when a kept reading stops being valid
- **Eliran's decision (2026-11-18): a kept reading stays valid across engine versions. It stops being valid when the reading tool or the model changes.** The plan's row said «the PDF's sha256 and the engine version»; with the version in the key every close of a milestone would throw every kept reading away. The row is corrected in place.
- **The reader is two files of the pipeline:** the reading tool (`Habait/tour360/tools/auto-trace.mjs`: what the model is asked, and how) and the file that names the model (`Habait/tour360/server/handler.mjs`: `TEXT_MODEL`). `readerOf(config)` = the sha256 of each, read from the disk at every question. A record holds the reader that made its reading; `found` needs both hashes equal to today's.
- **So:** a new engine version, another job, another mode, another day: the reading is still valid. One changed byte in either file: every kept reading is `stale`, and the next reading of each PDF is paid for once (by the operator's command, until a job can pay: milestones 4.2, 4.3). A change of either file is a listed port change (`pipeline/PORT-CHANGES.md`), so it never happens by accident; the milestone that makes one says that the kept readings go stale. **This milestone makes one** (section 3): readings kept before it, if there were any, are stale. There are none: no engine home has kept a reading yet.
- **An import** (section 4) is a hand saying «this is a reading of this PDF by today's reader»: its record carries today's reader and `source: imported`.
- When the reading tool or the model file cannot be read, there is no reader: `findReading` throws `TOOLCHAIN_MISSING`.

## 3. The same reading gives the same bytes of `plan.general.json`
Two things made the bytes differ between two runs of one reading. Each is now a function of the reading and the drawing only.
- **The day.** The reading tool wrote the day of the run into the plan (`plan_meta.trace_date`). It now takes the date as a flag, `--trace-date <YYYY-MM-DD>`, and writes the day only when none is given. This is the second listed change of the brought-in tool: one line, in `pipeline/PORT-CHANGES.md` with the new blob id (the closing test of 0.1 compares the file with that id).
  - `runTrace` takes `traceDate` and refuses anything that is not a real date written `YYYY-MM-DD`, before anything starts.
  - **A run from a kept reading hands the tool the record's `plan_date`:** the day that was written into the plan of the run that made the reading. A paid run that asks the model is handed today's day (UTC) by the command BEFORE the tool starts, and that same day goes into the record; so a run that crosses midnight between the model's answer and the plan cannot give a later run another date. An imported reading's `plan_date` is the day its own `_meta.at` says, or the day of the import when it carries none.
  - A run from a reading file with no record (`--vlm-file`) hands the tool the day of the reading's own `_meta.at`; a file that carries no date gets the day of the run, as before, and its plan is then not the same on another day.
- **The id.** The tool writes the id it is handed into the plan (`apartment_id`). A job handed it the job's id, which carries the engine version and the mode. **The stage now hands the tool the id of the DRAWING**, `drawingId(pdfSha256, apartment)`: sixteen hex characters made of the PDF's hash and the candidate, the same for every job of that drawing. (Contract 1.3 §3 said «`id` = the job id»; this replaces that line. A result is still read only when it names the id this run handed over.)
- **Pinned.** The hash of `plan.general.json` for the 846 fixture (the saved reading of 2026-11-06, the drawing's id) joins the pinned hashes in `tests/fixtures/apt846/expected-trace.json`, written by its generator from a real run. The command (1.2's closing test) and a job (1.3's) are both compared with it, on whatever day they run.
- **What is NOT promised to be the same bytes:** the files of an attempt that are not outputs of the stage (the tool's log, its debug images). The five outputs of the stage are the plan, the overlay, the report, the check file and the reading (contract 1.3 §3).

## 4. The command — `engine/cli.mjs`
- **`trace <pdf> --out <dir> [--id <id>] [--vlm-file <file>] [--no-judge] [--budget <usd>] [--go] [--fresh] [--json]`** (contract 1.2 §6, with the store).
  - **With `--vlm-file` the store is not asked and nothing is kept:** the file given is the reading, as in 1.2. `--vlm-file` with `--fresh` is a usage mistake.
  - **Without it, the command asks the store first.** `found` and no `--fresh`: the run reads from the kept reading, and no reading call is made, paid run or free. Then only the judge can cost: a free run needs `--no-judge` (else the `DRY` answer, which names the judge's calls only); a paid run with the judge on pays for the judge's calls and nothing else.
  - `none`, `stale`, `bad`, or `--fresh`: a reading call is needed, as in 1.2 (`DRY` unless paid). The answer says which of them it was.
  - **A paid run that made a fresh reading and ended `PASS` with one plan keeps that reading** (`source: paid`, `cost_usd` = the amount the reading itself carries for its call). A run that failed its check keeps nothing: its reading stays in the run's own folder. A free run keeps nothing.
  - The answer gains one fact: where the reading came from (`the store`, `the file given`, `the model`), the date it was read, and whether it was kept. Never its text.
- **`reading show <pdf>`** prints what the store holds for the PDF: the status of section 1, and for a pair that adds up the date it was read, its source, its cost, the model id, and how many readings were superseded. Exit 0 for `found`, 1 otherwise.
- **`reading import <pdf> <reading file> [--go]`** puts a reading a hand has into the store (`source: imported`, cost 0, today's reader). Without `--go` it writes nothing and prints what it would keep (root §5). The file must parse as a reading. A reading already kept is superseded, never overwritten.
- Usage mistakes exit 2, as before. Neither command prints a room name, a label or any other text of a reading.

## 5. The stage — `engine/stages/tracing.mjs`
- The stage of 1.3 asks the store: `findReading(config, job.input.pdf_sha256)`.
  - `found`: the free run of 1.3, with `vlmFile` = the kept reading, `traceDate` = the date it was read, `id` = `drawingId(job.input.pdf_sha256, job.input.apartment)`.
  - `none`: `failed` / `BUDGET_CAP`, the sentence of 1.3 (a reading has to be paid for, and a job does not pay for one yet).
  - `stale`: `failed` / `BUDGET_CAP`, its own fixed sentence: the kept reading of this PDF was made by another reader (the reading tool or the model changed), and a new one has to be paid for.
  - `bad`: `failed` / `STAGE_FAILED`, the sentence of 1.3.
  - In the last three nothing is started and no attempt folder is made.
- The outcome table, the stop, `review` and the outputs are those of contract 1.3. A job still never pays, and never writes into the store.

## 6. Settings (`engine.config.json`)
- No new field. `readingsDir` (1.3) is where the store is.
- **A number of the settings file is a JSON number** (the review of 1.3, O-3). `true`, `[4]`, `"0x3"` and `"3"` were taken for numbers because every value went through `Number()`; they are refused now, by name, for every numeric field of the file. The environment overrides (`ENGINE_SERVE_PORT`, `ENGINE_STUB_STEP_MS`) are text by nature and still take plain decimal digits.

## 7. The engine version
`package.json` `version` becomes `1.4.0`. A job's id carries the version (contract 0.2), so the same PDF starts a new job in 1.4. The drawing's id and a kept reading do not carry it (sections 2, 3).

## 9. What is NOT in 1.4
- **Paying for a reading inside a job** (milestones 4.2, 4.3). Until then a reading enters the store by the operator's paid command or by an import.
- **Keeping the judge's answers.** The judge is three vision calls, a report and not a gate; a paid run with the judge on pays for it again. A job runs with the judge off.
- **A booklet.** One reading per PDF: a job reads one drawing (contract 1.3 §8). The key of a booklet's drawings belongs to the milestone that reads booklets; the record's schema id is there for that day.
- **Everything else the reading depends on.** The reader is the two files of section 2. The steps before the model's call (the page scan, the crop of the drawing) are other files of the pipeline; a change of one of them is a listed port change too, and the milestone that makes it decides whether the kept readings still stand.
- **Cleaning the store.** Superseded readings are kept; nothing removes them.
- **A store shared by several engine homes.** Each home has its own; a working folder's is not the live home's.
- **The trace itself is not kept.** A second job of the same PDF runs the reading tool again from the kept reading (about a minute); only the model's reading is reused. The plan is the same because the tool is deterministic, not because it was copied.

## 11. The lock (after the two reviews; it replaces the lock FILE of contract 0.3 §10 rule 4)
The first review of this milestone found that the engine's file mutex (`withFileLock`, `engine/lib/atomic.mjs`, written at 0.3) is not exclusive between short-lived processes: eight processes that each took the lock once and exited gave two holders at the same moment in about a third of the runs, and eight commands keeping readings of one PDF at once could lose the record of a kept reading. The cause: a taker judged «the holder is dead» from text it had read a moment before, moved the lock aside to look at it, and the lock it moved was already another, live process's; for that moment the path was free. The mutex is the lock of a job's files, of the heavy lock's guard and of the readings store, so the rule is one, for all three.
- **The lock is a folder that holds ONE entry, named after its holder:** `h.<pid>.<taken at, in ms>.<nonce>`. It is there only while it is held. The name of an entry is never used twice, and nothing is ever renamed INTO the folder.
- **Every hold begins with the same ONE step, the only one the file system makes exclusive:** a folder prepared beside the path, with the taker's entry inside, is renamed ONTO the path. That fails when a folder is there: of two takers one wins. Measured on this machine (`development/tasks/3dengine/logs/1.4/gate3-rename-facts.txt`): of eight processes that rename a folder of their own onto one free path at the same moment exactly one is told it worked, in 30 rounds of 30.
- **Everything else only takes an entry OUT of the folder, by its own name:**
  - *release:* the holder's own entry is moved out; then the empty folder is removed (only an empty folder can be). A holder whose hold was broken finds its entry gone and touches nothing of the lock that stands there.
  - *a stale hold is BROKEN, never handed over:* the entry of a holder that is dead, or whose hold is older than `staleMs`, is moved out of the folder and the empty folder is removed. The lock is then FREE, and whoever wants it takes it by the one exclusive step. When that hold ended a moment before, its entry is not there and nothing is moved: the name of an entry can only ever mean the hold that was looked at.
- **Why a stale entry is not renamed to the taker's own** (the first form of this lock, `5c9b049f`, which the second review failed): a rename is exclusive on the name it CREATES, not on its source. Windows renames through a handle of the source, so processes that rename ONE source at the same moment are all told it worked (measured, same file: 234 of 240, up to 8 of 8 in a round). Four takers that waited for one killed holder all «took over», and ran together.
- **So no step looks first and acts on what it saw,** and nobody holds the lock except by the exclusive step.
- **What else can be at the path:** an empty folder (a release, or the breaking of a stale hold, that did not finish: removed, and the lock taken); a folder that holds something else (never emptied by the engine: `lock busy`); a lock FILE of the engine before 1.4 (by its old rules: a dead pid at once, an empty file after a second, any file after `staleMs`; then removed).
- **Stale** (`lockIsStale`): the pid of a dead process, at once; or a time further than `staleMs` from now, in EITHER direction (an entry that says it was taken far in the future, by a clock that was set back or by a hand, would otherwise never grow old).
- **What does not change:** `withFileLock(lock, fn, { waitMs, staleMs, label })` and the error `<label>: lock busy`. A holder that is ALIVE and silent for longer than `staleMs` still loses its hold, and still runs when it wakes (contract 0.3 §10 rules 9 and 11: the runner's ownership checks are what stops it from writing).
- **After an update of the engine no process of the older version may still run** on the same home: a lock file and a lock folder do not exclude each other. (Jobs of another engine version are other jobs; the heavy lock's guard is shared.)
- **Tests:** `tests/unit/lock-race.test.mjs`, with REAL processes: 64 short-lived holders with never two at once; a holder that DIES while eight takers wait, six times, and a LIVE holder whose hold grows older than `staleMs` while eight takers wait, four times: the takers go one after another, and the live holder's late release touches nothing (both fail on the first form of the lock, on a quiet machine too); four storms of eight keeps of one PDF, every record whole. `tests/unit/resilience.test.mjs`, as fixed sequences that need no load: the holder changes between a taker's look and its act (the hold ended and another took the lock; ended and nobody took it; taken again by the same pid), a broken hold is taken as a FREE lock (a new folder), a time in the future. And the mutex cases of `lib.test.mjs`. The tests that planted an empty folder as «a busy lock» plant a held one (`holdLock` in `tests/helpers/fakes.mjs`).
