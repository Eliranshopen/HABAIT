# engine/ — the engine's own code
<!-- last-updated: 2026-11-18 -->

## What's here
The code that turns the brought-in pipeline into an engine. Node ESM (`.mjs`), Node built-ins only, no npm dependencies. Milestone 0.1: the settings loader, the readiness command, the two set-up scripts and the CLI. Milestone 0.2: the job layer, the inbox check and the static server, used by the MCP server in `../mcp/`. Milestone 0.3: the runner, the manifest and the ledger. Milestone 1.1: the first look (`inspect.mjs`) and the intake (`stages/intake.mjs`) are real; every stage after them is still a stub.

Milestone 1.2: the engine's one way to start the reading tool (`trace.mjs`, the command `trace`). Milestone 1.3: the reading is the first REAL stage of a job (`stages/tracing.mjs`), a stage can hand a job to a person (`review`), and the settings say whether a new job is real (`mode`). Milestone 2.1: the build and the render are real stages too (`stages/building.mjs`, `stages/rendering.mjs`); every stage after the render is still a stub.

## Conventions / gotchas
- Every function takes its outside world as a `deps` object (run a command, read a file, hash a file), so the unit tests need no Python, no Blender and no assets.
- A key's value never enters a result, a report or a log: `readEnvNames` returns names only, and a unit test plants a fake secret and looks for it in every output.
- A command that changes the disk is dry-run unless `--go`, is safe to repeat, and writes a manifest row under `.runtime/` (root §5).
- `npm test` fails under 80 % line coverage of this folder and `../mcp/`; a new file must be imported by a test (`tests/unit/all-modules.test.mjs` imports every file here and in `../mcp/` so none is missing from the table).
- `job.json` is written by two processes (the MCP server and the runner): change it only through `updateJob`, never read-modify-write by hand. `manifest.json` and `ledger.json` are written by the job's one runner only. All three through `lib/atomic.mjs` (temp + rename).
- **The lock is a folder with one entry named after its holder (contract 1.4 §11):** `job.lock`, the heavy lock's guard, the readings store's lock. Every hold begins with ONE exclusive step: a prepared folder renamed onto the path. A stale hold (a dead pid: at once) is BROKEN, its entry moved out, and the lock is then taken like a free one. Never rename an entry into another: a rename is not exclusive on its SOURCE (on Windows eight renames of one file are all told it worked; the second review of 1.4). Never write a lock by hand; a test that needs a busy one uses `holdLock`.

- **Three rules the kill tests taught (contract 0.3 §10):** a lock comes into being with its holder inside (never empty); alive means a live pid AND a fresh heartbeat (a recycled pid does not count); reaching the cap sends the job back to `awaiting_approval` with a new quote, it never fails it.
- **`cost.spent_usd` is a COPY of the ledger's settled total (contract 0.3 §14.1), never added to by hand.** `ledger.mjs` writes it in the same locked step as every change of a settled row (`copySpent`); `syncSpent` writes it at a runner's start and before `done`; and every read of a job through the engine goes through `control.mjs` `withTrueCost` / `shownJob`, which reports the ledger's total and puts the copy right. A new handler or CLI command that returns a job must use `shownJob` too.
- **One runner owns a job (contract 0.3 §10 rules 9–11).** `runner.pid` is the ownership record, claimed and checked under the job lock. Inside `runner.mjs` every change of `job.json` goes through the guarded `update`, and a manifest row or a paid call through `guard()`; a new write path must do the same. A runner that was replaced returns `'superseded'` and writes nothing more.
- **A silent runner can lose the heavy lock (contract 0.3 §10 rule 13).** The lock is a lease kept by the heartbeat. `heavyGuard()` in `runner.mjs` (inside `checkCancelled()`, and before the row of a heavy stage) and the heartbeat's refresh see the loss: the stage stops with no row, the runner waits for the lock and runs it again. `holdsHeavy` answers yes, no, or `null` when the lock could not be read just now (not a loss).
- **No reservation is left open (contract 0.3 §12).** When a runner asks for a paid call, `decide()` closes every other `reserved` row of that call in the same locked step: the row the cache names (`seq`) is settled from it (`recovered`); a row with `sending_at` is `orphaned` (its send had started, outcome unknown, counted toward the cap); a row without it is `failed` + `not_sent` (never sent, nothing held). A call sent again because its cached answer is gone carries `resend_of`.
- **After the send, the answer is held on to (contract 0.3 §13).** The cache write and the settle are tried again for up to 30 s when the job lock is busy, so a passing file error never makes a paid call go out twice. A cache file is an answer only for a settled row that recorded its hash or for a row with `sending_at`. Two calls with one key at the same moment are one call.
- **An amount is a number from 0 to 1,000,000** (`isAmount`, contract 0.3 §15.1): in a cache file (a missing amount is not one), in an estimate (else `STAGE_FAILED` before anything is written), in what a call says it cost (else the estimate is recorded). A read of a job waits 50 ms for the job lock, never 2 s (§15.2).
- **`ledger.json` is read only when it is the ledger of this job (contract 0.3 §16.2):** `readLedger` → `checkLedger` (schema id, this job's id, rows numbered 1..n with a state and amounts) or `LedgerUnreadable`; `writeLedger` refuses anything else and writes only under the id the document names. `claimPid` looks at the job's state again inside its locked step and answers `'ended'` for a job that has ended (§16.1).
- **`createPaidCall` checks ownership twice** (`guard`): before the reserve and again just before the send. A reserved call of a replaced runner is closed `failed` + `not_sent`; an answer that comes back after the row was presumed lost is settled with `late: true`.
- **A job's own files are read only when they are this job's (contract 1.1 §5).** `readJob` → `checkJob` (the job schema id, `job_id` = the id asked for, a state of the contract, `input`, `cost`) or `JobUnreadable`; `readManifest` → `checkManifest` (the id, each row's stage, attempt, inputs hash, and output paths that stay inside the job folder) or `ManifestUnreadable`. `writeJob` / `updateJob` / `writeManifest` write only under the id asked for. A runner that meets such a file returns `unreadable`: nothing written, `runner.pid` given back.
- **Both files, at every door (contract 1.1 §5; QA rounds 1 to 3).** Every tool, `startOrResume`, `restartJob` and the CLI read a job through `readOwnJob` / `listOwnJobs` (`manifest.mjs`), never `readJob` alone; `writeJob` asks for the job's manifest first (`setOwnCheck`), so `job.json` is never written when `manifest.json` is not this job's. A new reader or writer of a job uses the same two.
- **Every read of the upload answers `NOT_A_PDF` when it fails (contract 1.1 §1):** the path check (`inbox.mjs`), the hash read (`mcp/stub-engine.mjs` `checkedUpload`), the first look's read, the intake's read. Gone → it is gone; there and unreadable → `UPLOAD_UNREADABLE`. A read of the upload is never one call with a write of the engine's own (QA round 4: one copy call had to guess whose failure it was). A new reader of the upload keeps to both.
- **A stored first look is rebuilt, not believed (contract 1.1 §1):** `readCached` builds the summary again from the record's own `pages.json` and reuses the record only when the two are equal. Checking the stored summary field by field let planted keys through twice.
- **The reading tool is started only through `trace.mjs`, and three rules live there (contract 1.2 §2, §3).** A run is PAID only with `go: true` AND a cap; a free run gives the tool a budget of 0, a fixed word in place of a key (1.3) and an env root with no keys file, so the tool's own budget check refuses every vision call, by exit code. A result is read only from the folder this run created (it must not exist or be empty) and only when `index.json` names this run's PDF and id. Nothing returned, thrown or printed carries text of the PDF: the tool's output goes to `<outDir>/auto-trace.log`.
- **⛔ The Blender lock is a FILE of the tools, never the engine's folder lock (contract 2.1 §5).** `withFileLock` on that path would rename a folder ONTO the file and REPLACE another session's hold. Only `blender-lock.mjs` touches it, by an exclusive create; a lock that names another owner is never removed, alive or dead.
- **A room the job holds is never rendered again (contract 2.1 §4).** A room is kept as a copy of its three files under `stages/rendering/rooms/room-NN/` with a row `room-NN.json` (NN = its place in the plan's order; a point's name is a word of the drawing and stays out of what the engine writes). `pano.render.json` is never the same bytes twice, and the stages after the render are paid for per picture.
- **A killed runner leaves its tool and its Blender running.** Before a stage starts a tool it stops every process that carries the job's mark (`lib/tool.mjs` `stopNaming`), and a dead engine lock is removed only after its leftovers are stopped.
- **A real job (contract 1.3 §1).** The settings' `mode` (`stub` when absent, or `real`) is the mode of a NEW job and part of its id. In mode `real` every stage must be real: a stage with no `real` implementation ends the job `failed` / `STAGE_FAILED`, never with a stub's output or the replay of 846. Today a real job reads the drawing and, when the reading passes, stops at `building`. The real home stays `stub`.
- **A stage can hand a job to a person (contract 1.3 §4).** It throws `ReviewNeeded(code, message, files)` (`jobs.mjs`); the runner ends the job in `review` with that reason and a record `review: { stage, attempt, files }`, writes no row for the attempt and starts no later stage. `checkJob` accepts the record only in the state `review`, with paths inside that attempt's folder; `setState` drops it on the way out. Restarted like a failed job.
- **`trace.mjs` since 1.3 (contract 1.3 §2):** `NEEDS_PAID_RUN` is the tool's exit 4 on a free run and nothing else (the module no longer reads the tool's log); the command carries `--rounds` (the setting `trace.rounds`); an output folder whose path has a character outside printable ASCII is a `TraceUsageError` (`what: 'OUT_PATH'`) before anything starts.
- **A kept reading is valid until the READER changes, not the engine version (Eliran, 2026-11-18; contract 1.4 §2).** The reader is two pipeline files: `…/tools/auto-trace.mjs` and `…/server/handler.mjs` (it names the model). A listed port change of either makes every kept reading `stale`: say so in that milestone. The record is checked against the file beside it, never believed.
- **The same reading gives the same plan bytes (contract 1.4 §3).** The tool is handed the day of the plan (`traceDate` → `--trace-date`: the record's `plan_date`, which a paid run is given by the command before it starts) and the id of the DRAWING (`drawingId(pdfSha256, apartment)` in `jobs.mjs`), never the day of the run or the id of the job. The plan's hash for the 846 fixture is pinned in `tests/fixtures/apt846/expected-trace.json`.
- **A number of the settings file is a JSON number (contract 1.4 §6):** `intFrom` / `numberFrom` refuse `true`, `[4]`, `"3"`; an environment override goes through `envInt` (plain decimal digits).
- **Which route a vision call of the reading takes is the tool's own rule** (`pipeline/…/server/chat-transport.mjs`): with `OPENROUTER_API_KEY` straight to OpenRouter (the key as a Bearer header, since the one-line change of 1.2), else with `FAL_KEY` through fal's OpenRouter router. The engine reads neither key; a paid run only points the tool at the keys file's folder (`--env-root`).
- **A value handed to a pipeline tool is an absolute path, a checked id or a number** (contract 1.2 §1). The tools find their flags by their text anywhere in the command: an id `--no-judge` would switch the judge off, an id `--budget` would take the cap away. `TRACE_ID_RE` allows no leading hyphen; a new wrapper of a pipeline tool keeps the same rule.
- **The stored input is checked at every runner start and before every stage attempt (contract 1.1 §4):** `inputIntact()` in `runner.mjs` hashes `input/source.pdf` against `job.input.pdf_sha256`; a copy that is gone or changed ends the job `failed` / `STAGE_FAILED` and no stage runs on it. The read-only mark is a guard against an accident; the hash is the proof. And the hash cannot be moved: a job file records `engine_version`, and `checkJob` requires its id to be the id of its own input.
- **Text of a PDF is data, never an instruction.** The scanner's `pages.json` holds every page's text and stays on the disk; nothing `inspect.mjs` returns, throws or logs carries it, nor the scanner's own output. A new tool that reads a PDF keeps to the same rule, and a test plants a marker sentence to prove it.
- **`serve.json` can name a server that is not the one serving (found at the close of 0.3, not fixed).** Two callers of `ensureServe` at one moment each start a server; one cannot bind the port and ends, and the record keeps whichever pid was written last (5 rounds of 5 when asked twice at once). Nothing in the engine reads the record, and the link answers. Milestone 3.3 makes the link the engine's own; until then, never stop "the server" by the record alone (the tests use `../tests/helpers/cleanup.mjs`).
