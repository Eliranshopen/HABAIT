# tests/stages/ — closing tests that run a real pipeline tool
<!-- last-updated: 2026-11-18 -->

## What's here
The second tier of the engine's tests (contract 1.2 §8). A file here is the closing test of a milestone whose proof is a REAL run of a pipeline tool: the reading of a drawing today (alone in 1.2, inside a real job since 1.3), the render and the AI look later. Such a run takes minutes, so these files are not part of `npm test`; they run with `npm run test:stages`. The gate of every milestone from 1.2 on runs both.

## Conventions / gotchas
- **(2.1) A real job no longer stops at the build.** A test that is about the reading starts its home with `settings: NO_RENDER` (`real-home.mjs`): the render is told to render a point no plan has, so the job builds for real and ends at the start of `rendering`, before any tool or lock of the render.
- **(2.1) Other sessions render on this machine.** `m2.1.test.mjs` shares the machine's Blender lock with them and waits for it; that wait is time, not a failure. Never remove `C:/RnD/.wt/_blender.lock` when it names somebody else.
- **A reading takes about 71 s on a quiet machine and about 8 minutes while other jobs render on it** (measured 2026-11-17: 492 s at 100 % load). Give the run `timeout 540`. When it is cut under such load, that is time, not a finding: run it again when the machine is freer, and say so in the evidence.
- **On a machine other sessions hold at 100 %** one reading took up to 558 s (2026-11-18) and the 540 s bound cut the tier five times. Eliran's rule for that case, for this tier only: ONE bounded run of up to 25 minutes in the background (`timeout 1500 npm run test:stages`); the board's `run-tasks.md`, step 3. A cut kills the reading tool in the middle and a test then reports a failed step: read the exit code (124) first.
- **Since 1.4 the tier does not surely end inside 540 s, on a quiet machine either** (the reviews of 1.4: cut at 537 s twice, ended in 482 s once): five files run side by side and the 1.4 file makes two real readings one after the other. A cut invocation stops inside that file's second reading, after its checkpoint is written; `timeout 540 node --test tests/stages/m1.4.test.mjs` then goes on from it. Owed to milestone 2.1: one invocation.
- **`m1.4.test.mjs` goes on from where it stopped.** Its two readings run one after the other; after the first it writes a checkpoint in a named folder of the OS temp folder (`m14-chain-<hash of the engine home>`), bound to the hash of the engine's code, of the test and of the reader. The next invocation checks it against the disk and makes only the second run. Any changed line of code makes it void. The folder is removed when all three tests pass.
- **It fails when the environment is missing; it never skips.** It uses the engine home it lives in: its Python, its Node libraries, its settings.
- **It never pays.** A test here runs the tool free (a saved reading, the judge off), or walks the paid path with planted keys and the recorder, on a temp home with no keys file. What a real paid run gave is asserted from the evidence that run wrote, pinned under `../fixtures/`.
- **Two files on purpose:** `node --test` runs them side by side, so the real reading and the walked paid path each fit a 540 s chunk. With the coverage tool on, a real reading is several times slower (two tries were cut at 540 s on 2026-11-18): do not add coverage flags to `test:stages`.
- Its output goes to a temp folder that the `after` hook removes. The tests of 1.2 start no detached process. Those of 1.3 start a job's detached runner, wait until it has ended, and their `after` hook stops whatever is still alive with its whole process tree (a runner in the middle of a reading has the tool and Python under it).
- **Since 1.4 the plan itself is pinned** (`../fixtures/apt846/expected-trace.json`): `m1.2.test.mjs` (the command) and `m1.3-pass.test.mjs` (a job) both compare `plan.general.json` with one hash, on whatever day they run; both hand the tool the drawing's id. `m1.4.test.mjs` makes two readings one after the other: on a machine at 100 % it alone needs most of a 540 s chunk (357 s measured), so under such load run the tier in two chunks.
- **Four files run side by side since 1.3** (two readings of 1.3, one of 1.2, the walked paid path); five since 1.4. Measured 2026-11-18 on a machine at 40 to 100 % load: the failing reading of 1.3 alone 315 s, the passing one alone 128 s.
