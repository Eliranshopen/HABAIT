## Observations
- O-1 (section 5 / milestone 0.3, `job.lock`): three times in 8,566 raced calls, `start_simulation` on an existing job answered JSON-RPC `-32603 internal error in start_simulation: job <id>: lock busy` (no path in it). Each time the swapper was running (folder, remove, other-PDF modes) and the machine was at 100 % with real Python scans going; it did not occur in the control without a swapper (300 calls), in hard-link (1,000), junction (1,500) or in a second folder run of 3,000. `withJobLock` waits 2 s; a runner heartbeat or a starved process held the lock longer. It is not an upload read, I could not reproduce it on demand, and section 9 names only the lock-as-a-folder case; so I did not fail on it. Worth a line in section 9: "lock held for over 2 s → `lock busy` JSON-RPC error". Evidence `qa5-b1-race-folder3000.txt` (the clean run) and `qa5-b1-race-other-modes.txt`, `qa5-b1-race-other-killed.txt`.
- O-2 (section 8, test 10): at 100 % load the lock-holder test failed on a wait in 2 of 6 full runs (its 150 s allowance for a PowerShell process to start). Passes alone in 36 s. A test about time, not the engine; a longer allowance, or starting the holder before the server, would remove it.
- O-3 (section 8 / the gate): at 100 % load neither `npm test` under `timeout 300` nor the m1.1 file under `timeout 280` finishes reliably (260 s on a quiet machine, 300 s cut under load). The gate summary should state its cap. Under the cut, `npm test` leaves detached `engine/cli.mjs serve` processes of the `m03` tests behind (I found and stopped 19 of my own; clean runs leave none).
- O-4 (section 1, two readings): "a stored first look is reused without starting Python". With a record that is true and a Python path that does not exist, both tools answer `TOOLCHAIN_MISSING` ("the engine's Python is missing: <path>") because `inspectPdf` checks that Python exists before it reads the record. Reading A (the sentence is about not starting a process): satisfied, round 4 proved it with a Python that exists but cannot scan. Reading B (a missing Python does not matter when the record is true): not what the code does. The failure list in section 1 names a missing Python as `TOOLCHAIN_MISSING`, so the code follows reading A. The message also carries the configured path (a config value, not PDF text).
- O-5 (section 1): a first look of half-written bytes takes 7 to 62 s per call under this load (my homes allow 120 s; the product's limit is 30 s and answers `FILE_TOO_LARGE`, section 9).
- O-6 (section 0.2 inbox, carried from round 4): `s.pdf::$DATA` (an alternate data stream of a file in the inbox) is accepted as the same file. Not a defect.
- O-7 (section 1, a gap, not tested as a break): the size limit is checked once, at the check of the path. A PDF replaced by a file over 20 MB between that check and the read would be read whole and hashed as it stands; I did not build that race (it needs a 20 MB writer in the tens-of-milliseconds window).
